## 〇、本轮定调

两句话锁死产品的形状：

1. **不做插件、不做场景特化。** 骨架纯通用——ERP、TT、留言板都只是往里填的内容，不进架构。
2. **形态是"按需部署一套"。** 要验证什么项目，就部署一套系统。一次验证 = 一套独立系统。

> 产品本体：**把一段自然语言，快速变成一套能跑、能操作、能访问的业务系统**——用完即弃，随时再部署。

## 一、产品形态：一验证，一部署

心智从"管理一堆项目"转向"**拉起一套环境**"：

```
想验证一件事
   ↓ 说一遍（自然语言）
部署一套系统（自带数据 或 连已有数据）
   ↓ 秒级就绪
给它一个入口 → 用 / 演示 / 给别人访问
   ↓ 验证完成
销毁（或保留为常驻）
```

**每一个部署都是独立的一套房**——独立数据、独立入口、互不干扰。这是产品最该被用户"体感"到的事实：**折腾是安全的，因为隔离。**

## 二、首页 = 部署清单

首页不是"项目管理器"，是"**我部署过的系统们**"。主按钮只有一个。

```
┌──────────────────────────────────────────────────┐
│  DataMason                          [+ 部署一套系统]│
├──────────────────────────────────────────────────┤
│  运行中                                            │
│  ┌────────────────────────────────────────────┐  │
│  │ 留言板 · 验证「访客反馈收集」                  │  │
│  │ ● 运行中 · 2 小时前部署 · 12 条数据            │  │
│  │ 入口：http://192.168.x.x:port/app/guestbook      │  │
│  │                                  [打开] [演示]  │  │
│  │                                  [停止] [销毁]   │  │
│  └────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────┐  │
│  │ 进销存原型 · 验证「库存周转」                  │  │
│  │ ● 运行中 · 昨天部署 · 340 条数据              │  │
│  └────────────────────────────────────────────┘  │
│                                                    │
│  已停止 / 历史  ▸（折叠，默认不打扰）               │
└──────────────────────────────────────────────────┘
```

设计要点：
- **一套 = 一张卡**：名称（业务化的）、验证的是什么、状态、数据量、入口、动作。
- **动作按使用频率排**：打开 / 演示 高频放前，停止 / 销毁 低频放后，销毁给二次确认。
- **已停止的默认折叠**——"用完即弃"不应该堆成一个越来越长的列表。
- **主按钮唯一**：`[+ 部署一套系统]`。产品只有这一个入口，清清楚楚。

## 三、部署流：一屏三步

```
① 你要验证什么？
   「做个留言板收集访客反馈」                    ← 一句话输入
   数据：●从零建 ○接已有的（下阶段开放）          ← MVP 期直连置灰（DR-09）
   ↓
② 系统设计提案                                  ← 生成即提案
   ┌──────────────────────────────────┐
   │ 我准备这样建：                       │
   │  · 留言表（访客、内容、时间、状态）      │
   │  · 界面：访客留言页 + 后台管理页        │
   │  [关系缩略图]  ☑ 附带演示数据           │
   │ [就这么部署] [调整一下] [换个描述]      │
   └──────────────────────────────────┘
   ↓
③ 部署中…（秒级）
   建库 → 建表 → 生成页面 → 演示数据 → 注册入口   ← 注册入口，不是起服务（DR-15）
   ↓
✔ 就绪：一套系统跑起来了
   入口：http://192.168.x.x:port/app/guestbook    [打开] [演示]
```

设计纪律：
- **部署进度要可见、但不拖**。秒级的事情不要假装很复杂——进度条是"让你看见它真的在干活"，不是表演。
- **提案里出现的内容都是业务话**（"留言表""后台管理页"），不出现"表结构""CRUD"这类词。
- **部署完成 = 给出入口**。用户立刻能点开、能分享。这是"从说到跑"闭环的最后一厘米。
- **就绪即带演示数据（DR-08）**：默认附带（提案页可关），让"数据会说话"从第一秒成立；工作台可一键清空种子数据。
- **入口显示部署主机实际地址**（DR-17）：MVP 限单机/局域网，不写死 datamason.local。

## 四、一套 = 一个独立环境

| 维度 | 设计含义 |
|---|---|
| 数据 | 自带独立库（创建模式），或连接外部数据（直连模式，M2/P1 起）——两者都收在"这套系统"里 |
| 入口 | 每套有自己的访问地址，可给他人访问（演示 / 真实使用；MVP 限本机/局域网） |
| 生命周期 | **五态（DR-13）**：草稿 → 部署中 → 运行中 → 已停止 → 已销毁；**演示是运行态下的视图模式，不是状态** |
| 隔离感 | 视觉与措辞都要让用户确信"这套坏了不影响那套" |

**草稿态定义（DR-13）**：部署流进行到「提案未确认」即为草稿——只存在于会话内，不进部署清单、离开即弃；确认瞬间转部署中。用户感知上"反悔零成本"：没确认就什么都没发生。

**销毁要轻、要干净**：一键，给二次确认，附一个"先导出数据"的机会。因为"用完即弃"是产品承诺的一部分——**弃得干净，才敢建得大胆**。

## 五、两种数据模式嵌在部署里

上一轮的"数据创建 / 数据直连"两种模式，不改动，只是归位到部署流的第一步：

- **创建（MVP，M1 即有）**：这套系统自带数据 → 部署时就建好库和表。
- **直连（M2/P1 交付，DR-09）**：这套系统连已有数据 → 部署时接上外部数据源，只做界面与操作层。MVP 期部署流第一步只提供「从零建」，「接已有的」置灰并提示"下阶段开放"——避免选了之后无路可走。

部署流的第一步（"你要验证什么"）旁边，多一个小小的选择题：**"数据从零建，还是接已有的？"**——不叫"模式"，就是一句人话。

## 六、一套系统内的成员与权限（必做，不是可选项）

一套部署不是只给创建人自己用的——**验证项目往往要拉上小团队真用起来**。所以每套系统内建三层角色：

| 角色 | 能做什么 | 定位 |
|---|---|---|
| **创建人** | 一切：改模型/改界面、配权限、加成员、停止/销毁/分享 | 系统的主人 + 建造者 |
| **管理员** | 全套业务功能（所有菜单页面）+ 数据管理（导出、维护、处理异常记录）+ 查看成员与日志；**不含工程室、不含停止/销毁/分享**（DR-14，2026-09-15 统一） | 管事的、监督的 |
| **操作员** | 仅操作**分给自己的功能**，看不到没分的部分 | 一线干活的人 |

**授权按人，不按角色（DR-02）**：同样是操作员，小李分到"入库单+库存查询"、小张分到"质检单+退货处理"——分的是"功能给某个人"，不是"功能给某个角色"。角色只定档位（创建人/管理员全量，操作员=自己的授权集合）。

### 权限配置的交互：不做 RBAC 矩阵，做"把功能分给人"

```
成员与权限 · 库存管理系统
┌──────────────────────────────────────────────┐
│ 创建人  老猫（你）                             │
│ 管理员  王姐   —— 查看所有功能                 │
│ 操作员  小李   —— ☑ 入库单 ☑ 库存查询          │
│ 操作员  小张   —— ☑ 质检单 ☑ 退货处理          │
│                               [+ 添加成员]     │
└──────────────────────────────────────────────┘
```

- 创建人打开"成员与权限"，看到**功能菜单树**，勾选分给**某个人**（不是分给角色）。人话、直观，不出现"权限/角色/数据域"这些词。
- 添加成员的入口：输入对方账号（或生成一个访问链接，对方进入即绑定身份，M3/P2）。**成员增删与授权变更是创建人独有动作**，管理员可见名单但不可改（DR-14）。

### 三个设计要点

1. **界面按角色裁剪**：操作员登录后看到的，只有分给自己的那几个菜单。裁剪不只是安全——**也是清爽**，每人只见自己要用的（授权按人存储，见本文档 §十一 七）。
2. **创建人独有"工程室"入口**；管理员是"高级使用者"（全套业务功能 + 管理动作）；操作员是"受限使用者"。与 v0.1 的可见性模型正好衔接：创建人 = 建造者视角，管理员/操作员 = 使用者视角的两种档位。
3. **数据级权限起步做简单版**：操作员看得到自己录入的记录（"我的记录"入口），整套系统的全量数据归创建人/管理员。复杂的行级权限以后再说，MVP 不碰。直连的外部表若缺归属列，则"我的记录"对该表降级并在界面明示（技术上**绝不对外部库补列**，见本文档 §十一 四）。
4. **访客不是第四个角色（DR-04）**：除三层成员外，`公开页面`（如访客留言页）允许**匿名访问者**提交内容——访客看不到任何菜单与数据，只能提交到公开页面。访客公开页面 M3/P2 交付；MVP 期留言由成员在后台管理页代录。分享=定板支持（2026-09-15），MVP 限本机/局域网，绑定身份的链接 M3/P2。

## 七、每套系统内建操作日志（固定能力）

验证项目一旦拉上小团队真用，就会冒出同一类问题——"这条订单是谁改的？""那张退货单什么时候被删的？""王姐昨天到底处理了哪几条？"。靠人脑记、靠群里问都撑不住。所以**操作日志是每套系统自带的固定件**，跟"我的记录"一样，不是要谁去配置、去开启的东西：部署一就绪它就在，用户一张表都没建它也在。

它要回答的问题只有一个：**关键事件发生时，能还原出"谁、什么时候、在哪类业务上、对哪条记录、做了什么"**。

### 记什么、不记什么

| 类别 | 记 | 不记 |
|---|---|---|
| 业务数据 | 新增、修改、删除（含改了哪几个字段、改前改后值） | 只读浏览、筛选、查询 |
| 部署生命周期 | 部署、停止、再启动、销毁；成员增删与角色变更；表结构（蓝图）变更 | 纯查看类动作（看蓝图、看日志本身） |
| 问数据 / AI | 执行了哪些写入型动作（若以后开放）；纯问数据本身不记 | 每一次问答的浏览过程 |

修改要能看到**字段级差异**（"单价：38 → 42"），删除要留下可辨认的摘要（记录已不在，但日志里知道删的是哪一条、关键内容是什么）。只读动作一律不记——日志是"发生过什么事"的流水，不是行为监控，记一堆"谁看了哪页"既吵又没用。

### 呈现与查阅

- 入口在每套系统内常驻（创建人/管理员可见的"操作日志"菜单），按**时间倒序**，像翻阅流水一样翻阅。
- 每条一行，字段固定：**时间 · 谁 · 做了什么 · 哪条业务记录**；点开看字段级改动明细。
- 支持最朴素的筛选：按人、按业务对象（哪张表/哪个功能）、按动作（新增/修改/删除）、按时间段。
- 从一条业务记录上能直接跳到"它的来龙去脉"（记录详情里的"操作记录"入口），也能从日志点回那条记录——两个方向都通，追溯才顺手。

### 三条底线

1. **只追加**：日志一旦写下，界面上不能改、不能删。它的全部价值就在于"不能事后抹平"。
2. **随部署生灭**：日志属于这套系统，停止不丢、销毁时随数据一起清掉；销毁前的"导出数据"一并含日志。
3. **按角色可见**：创建人/管理员看全部；操作员只能看到自己那部分动作。它是给管事的人还原现场用的，不是全员公示栏。

> 优先级随业务操作一起落地（P1）：没有增删改和成员协作，就没有东西可记；一旦多人真用，它必须已经在。导出日志随销毁/导出能力走（P2）。

## 八、数据层（架构假设）

秒级建库、连接管理、读写直连——这些"说起来轻巧"的能力，由产品自研的数据层承担，不依赖任何外部工具运行时。设计上不展开技术，但架构假设要记一笔：

- 部署的"建库/建表/起服务"由自研数据层执行（SQLite/MySQL/PG 直连）→ 秒级就绪才有底气；
- "数据直连"模式复用自研连接管理（MySQL/PG/SQLite）→ 不用重新发明，也不用绑定外部工具；
- 能力设计参考 DBX 等成熟数据库工具的交互与安全模式（自然语言生成结构/查询、AI 产物执行前审查），但**不接入、无运行时依赖**——数据资产始终是用户自己的。

## 九、与 v0.1 骨架的衔接（不变的部分）

- **三段旅程**：说 → 看 → 用，仍成立；"部署"就发生在"看"到"用"之间。
- **生成即提案**：部署前的设计提案，就是这条原则的又一次落地。
- **AI 三形态**：指令层负责"部署一套"，问答层在工作台里用。
- **演示模式**：每套系统的"展厅"，一键从工程室切过去。

**v0.2 只加了一个概念：部署。** 其余骨架照旧，不叠加。

## 十、已决策（2026-09-15 定板）

1. **默认保留 + 一键销毁**：部署默认保留、不做自动清理（验证结果本身有价值）；用户主动一键销毁，销毁前给导出机会。
2. **停止 / 销毁分开**：停止 = 保留数据可再启动；销毁 = 数据一并清掉。两态分开，给用户安全感。
3. **只做 Web 版**：架构 Web-first 且不做桌面端，Tauri 桌面壳不再作为后续选项。本地 SQLite 由 Web 服务端进程管理，对用户透明。
4. **图表自绘（ECharts，规格驱动）**：问数据的图表能力自研轻量封装，**不联动 superset-lite**。
5. **操作日志内建（固定能力）**：每套部署自动记录业务数据增删改与关键系统动作，只追加、按角色可见，随业务操作（P1）交付（2026-09-15 新增，详见第七节）。一致性由两阶段写入 + 启动对账保证（DR-03，见本文档 §十一 五）——业务库与元数据库是两个库，不存在跨库事务。
6. **分享定板支持 + 访客（DR-04，2026-09-15 关闭原待确认项）**：每套部署入口可分享给他人（演示/使用）；MVP 限本机/局域网，分享链接绑定身份 M3(P2)；访客=匿名访问者，仅公开页面（M3/P2）；MVP 期留言由成员代录。
7. **权限按人授权（DR-02）**：存储为"菜单→某个人"的授权集合，角色只定档位；同角色不同菜单。
8. **里程碑编号唯一（DR-01）**：M0–M4 以本文档 §十一 十 为准（M1–M4 对应 P0–P3，M0 为独立技术验证里程碑）；体验文档用 UI-n 标注界面次序；提案卡简版前移 M1；直连模式归 M2。
9. **建表管线注入归属列（DR-05）**：创建模式每张业务表强制带 created_by 等四列（P0 就位，P1"我的记录"的物理前提）；直连表缺列则降级明示，不 ALTER 外部库。
10. **就绪即带演示数据（DR-08）**：部署管线含种子数据步骤，默认附带、可关、可一键清空。
11. **网络可达性（DR-17）**：MVP 限单机/局域网，入口显示部署主机实际地址；公网不做，P2 评估。
12. **流程=向导式 v0（DR-06）**：页面步骤 + 状态字段推进，不做工作流引擎，M3(P2) 交付（一页纸的流程承诺相应从 P1 调整到 P2，见《产品一页纸》§九）。

**仍待确认（0 项）**：原「入口是否支持分享给别人」已定板支持（第 6 条）。当前无开放问题；新的跨文档决策按《产品一页纸》§九 四 维护规则追加 DR 条目。

### 〇、路线总纲：与 superset-lite 对齐的五条纪律

superset-lite 用一套可复用的方法把「AI 生成」落到了可治理的产品里。DataMason 直接继承这套方法，不另起炉灶：

| # | superset-lite 已验证的做法 | DataMason 的对应 |
|---|---|---|
| 1 | **LLM 只产中间规格，Python 确定性映射落库结构**（chart_spec → form_data_builder），不让 LLM 直接吐易碎结构 | LLM 产 **表规格 table_spec**（表/列/约束/业务标签），Python 映射出 DDL、页面清单（page_specs，DR-07）、CRUD 配置、UI 配置；查询链路复用 superset-lite 的 generate_sql 规格模式 |
| 2 | **OpenAI 兼容 LLM 网关**（temperature=0、schema context 注入主外键/comment/采样值、sqlglot 只读门、自检重试、token 埋点） | 同款网关迁移到 DataMason 后端（含 NL→SQL 查询生成，即产品文档的「问数据」内核），模型表惰性建表 |
| 3 | **隔离纪律**：业务代码只进 `biz/`，核心树只加一行注册；依赖按 `base` / `-ai` 分开 | DataMason 独立 repo，内部严格分「核心数据层 / 业务编排层」；以 superset-lite、DBX 为**参考基线但零运行时依赖** |
| 4 | **惰性建表**：`Model.__table__.create(bind, checkfirst=True)`，不动 alembic | DataMason 元数据表全部走惰性建表，秒级部署不需要迁移框架 |
| 5 | **探索式验证**：每个能力落地必须「离线纯函数测试 + 真实 LLM + 真实浏览器」两级验收 | 沿用，里程碑自带验收标准 |

**一个明确的差异点**：superset-lite 是「一个平台」，DataMason 是「一套套独立部署的系统」。所以 DataMason **不把 superset 当宿主**，而是继承它的方法与前端图表资产，核心服务自己实现（轻量、秒级、可销毁）。

**移植清单（DR-18）**：以下 superset-lite 0.2.0 资产按「能力契约」移植——**开工前确认 0.2.0 源码可得**；任一项不可得时按右列契约自实现，里程碑不变：

| superset-lite 资产 | 移植到 | 能力契约（不可得时按此自实现） |
|---|---|---|
| `superset/llm/api.py`（网关设计） | `server/llm/` | OpenAI 兼容端点、temperature=0、schema context 注入、自检重试、token 埋点 |
| generate_sql 链路（schema context + sqlglot 只读门） | `server/llm/` + `server/qa/` | NL → 只读 SELECT，执行前安全审查 |
| `_select_relevant_tables`（两段式选表） | `server/dataaccess/` | 直连模式 schema 过大时的相关表筛选 |
| `AiGeneration` / AiAssets 页设计 | `ai_generations` 表 + web 生成历史页 | kind 扩展、token/duration/status 埋点、生成资产清理 |
| 惰性建表手法（`checkfirst=True`） | `server/models/` | 全元数据表免 alembic 启动建齐 |

### 一、总体架构

```
┌─────────────────────────── DataMason Web（React 18 + TS + antd + Vite）────────────────────┐

┌───────────────▼─────────────────────────────────────────▼──────────────────────────────────┐
│                        DataMason Server（Python 3.12 + Flask + SQLAlchemy 2.x）             │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ ┌─────────────┐          │
│  │ LLM 网关    │ │ 元数据服务   │ │ 结构/查询   │ │ 部署管线     │ │ 权限/成员   │          │
│  │ (NL→结构    │ │ (deployment │ │ 生成器      │ │ (jobs+状态)  │ │ (三层角色)  │          │

│  └─────────────┘ └─────────────┘ └─────────────┘                                           │
│  ┌───────────────────────────────────────────────────────────────────────────────────────┐ │
│  │ 数据层（自研）：connections 连接管理（加密存储）· 多方言 SQL 执行器 · schema 反射        │ │
│  │   dialect: SQLite / MySQL / PostgreSQL（MVP）＋ superset db_engine_specs 为方言层参考 │ │
│  └───────────────────────────────────────────────────────────────────────────────────────┘ │
│  元数据库（SQLite/PG, 惰性建表）：users · connections · deployments · table_specs ·      │
│      page_specs · crud_configs · flow_specs · deployment_menus ·                          │
│      deployment_menu_grants · deployment_members · ai_generations · activity_logs          │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

**分层原则**：
- DataMason Server 是唯一大脑：管连接、规格、元数据、编排、权限。**连接与执行全部自研**（SQLAlchemy 多方言），不依赖任何外部数据工具运行时。
- 各部署的运行时数据 = 独立物理库（SQLite 文件）或独立 schema（MySQL/PG），连接规格存 `connections` 表（加密），与元数据库分开。
- `LLM 网关` = 两个能力面的同一底座：**NL→结构**（product 的建表/改表）与 **NL→查询**（product 的问数据）共用网关，结构链路多了规格→DDL 的确定性映射。
- **DR-03 注意**：业务写发生在部署的独立物理库、日志在元数据库，**两库无共享事务**——任何跨库原子性承诺都不成立，日志一致性按 §五 的两阶段写入 + 启动对账实现。

|---|---|---|
| 后端框架 | **Flask 3.x + SQLAlchemy 2.x** | 与 superset-lite 后端同构，LLM 网关/惰性建表经验直接迁移；单机工具无需 FastAPI 的 async 收益 |
| 规格校验 | **pydantic v2**（不引 marshmallow） | table_spec / crud_spec 校验路径独立于 superset，pydantic 模型即文档 |
| LLM 网关 | 移植 `superset/llm/api.py` 设计 | OpenAI 兼容端点、`temperature=0`、schema context、自检重试、token 埋点；模型表 `llm_models` 惰性建表、api_key 加密存储 |
| 数据层 | **自研**：SQLAlchemy `create_engine` 连接管理 + `inspect()` schema 反射 + dialect 感知 DDL | 参考 superset 的 `Database` 模型（连接串加密、dialect 探测）与 `db_engine_specs` 的方言组织；MVP 锁 SQLite/MySQL/PG，SQLAlchemy 方言天然支持 |
| 前端 | **React 18 + TS + antd + Vite** | superset-lite 前端是 React+TS+antd；构建器换 Vite：DataMason 不背 112M superset-frontend，秒级构建对部署体验重要 |
| 图表 | **ECharts（规格驱动封装，自绘）** | MVP 不涉及；P3 问数据时自绘轻量图表，避免整套 superset 图表链路。**已定：不联动 superset-lite**（2026-09-15 决策），专业看板需求以后另议 |
| CRUD 引擎 | **自研「元数据驱动」通用引擎**（不引第三方 CRUD 框架） | 与「规格→确定性映射」哲学同构，无重依赖；表格交互细节参考 DBX 数据表格（排序/过滤/导出） |
| 元数据库 | **SQLite（默认）/ PostgreSQL（可选）** | 对齐 superset 元数据库模式；惰性建表不动 alembic |
| 部署形态 | **单服务 + 多 deployment 逻辑隔离**（每套独立物理库/独立 schema） | 秒级部署不能每套起进程；数据隔离靠物理库边界；进程/Docker 级隔离留 P2 选项 |
| 测试 | **pytest（离线纯函数）+ 真实 LLM E2E 脚本 + Playwright** | 完全沿用 superset-lite 0.2.0 的测试分层 |

### 三、参考项目清单：DBX 能力 → DataMason 对应实现

DBX 不是底座，是**能力对照表**。以下每行都是「DBX 做了什么 → DataMason 自己做时参考什么」：

| DBX 能力域 | DBX 的做法 | DataMason 的对应实现 | 参考要点 |
|---|---|---|---|
| **NL 生成数据结构**（老猫点名） | AI SQL 助手：选中表 + 一句话需求 → 生成 SQL（含 DDL 变更） | **table_spec 链路**：业务描述 → 表结构规格 → 确定性 DDL（比 DBX 更进一步：从「改查询/改单表」扩展到「从零设计一整套结构」） | 交互模型：一句话输入 → 生成预览 → **执行前审查确认**；DataMason 的「生成即提案」就是它的强化版 |
| **NL 生成数据查询**（老猫点名） | 选中表 + 自然语言 → SELECT；AI 解释/优化/修复 SQL | **问数据链路**：自然语言 → SELECT（继承 superset-lite 的 generate_sql：schema context + sqlglot 只读门 + 自检重试），结果以视图卡呈现 | **安全检查模式**：DBX 在 AI SQL 执行前用内置安全检查审查——DataMason 全链路继承（只读校验 + 执行前确认） |
| 连接管理 | 90+ 方言连接、SSH 隧道、连接导入（DBeaver/Navicat） | 自研 `connections` 表：dialect/连接串（加密）/连接测试；MVP 只做 SQLite/MySQL/PG 新增与只读状态（对齐产品文档 M4 收敛版） | superset `Database` 模型为准；连接导入（DBeaver/Navicat）P2 可参考 DBX 思路 |
| 表结构编辑器 | 可审查的字段与索引变更（非直接 DDL） | 数据蓝图「逐张修改」：以提案卡呈现变更 diff → 确认后执行 `ALTER` | **审查式变更** vs 直接 DDL——DataMason 的提案卡模式即此思路的产品化 |
| 数据表格 | 虚拟滚动、WHERE/ORDER 控件、右键过滤、行内编辑、导出 CSV/JSON/MD/XLSX | CRUD 引擎列表页组件（排序/筛选/分页/导出） | 表格交互细节直接照抄可用项（排序、过滤条、导出格式） |
| ER 关系图 | Schema 工具中的表间关系可视化 | 数据蓝图业务化 ER 图（动词标注关系，对齐体验文档 5.3） | 可视化呈现与布局算法可参考 |
| Schema 对比 / 数据迁移 / CSV 导入 | 跨库对比、库间迁移、CSV/Excel 导入 | **P2+ 备选**（DR-16）：不绑定里程碑，元数据模型留扩展点 | 触发信号=真实场景出现（体验文档命令层"Excel 导入"联想词是需求线索），不预设排期 |
| Redis / MQ / Mongo 专项 | 专项浏览器与命令执行 | 不做（超出「验证型信息化」范围；如未来需要走 superset 生态或自选） | — |

**结论一句话**：DBX 证明「AI 原生数据库工具」的交互与安全模式是可行的，DataMason 把这些模式**收编进自己的规格驱动架构**，并且向上走了一层（从「管理已有库」到「从业务想法生成整套结构」）。

### 四、核心机制一：自然语言建表管线（P0 心脏）

完全复刻 superset-lite 的「中间规格 + 确定性映射」链路：

```
用户一句话「做个留言板收集访客反馈」
  │
  ├─① LLM 网关生成 table_spec（JSON, LLM 只产这个）
  │      { tables: [ { name, biz_name, columns:[{name,biz_name,type,nullable,
  │          default,is_pk,is_fk,ref_table,ref_column}], indexes } ],
  │        biz_notes: "每张表是干什么的" }
  │
  ├─② 规格强校验（pydantic）：类型白名单、主键唯一、外键引用存在、无孤儿表
  │     校验失败 → 中文原因回喂 LLM 重试（对齐 SQL 自检重试模式，上限 2 次）
  │
  ├─②b 归属列注入（DR-05，确定性、不经 LLM）：创建模式下，ddl_builder 为每张业务表
  │     强制补 created_by/created_at/updated_by/updated_at 四列（若 LLM 已给出则不重复）。
  │     这是 P1「我的记录」（WHERE created_by = 当前用户）的物理前提，必须在 P0 就位。
  │     直连模式的表若缺这些列：该表数据级权限降级（操作员不可见"我的记录"筛选），
  │     在界面明示，且**绝不对外部库执行 ALTER 补列**。
  │
  ├─③ 确定性映射 ddl_builder：table_spec → 方言化 DDL
  │     （SQLite/MySQL/PG 三方言；外键规范统一生成，索引/备注/缺省值一并落）
  │
  ├─④ 数据层执行建表（自研 executor, 经 connections 选定目标库, execute 批量 DDL）
  │     失败逐表回滚语意化报错
  │
  ├─⑤ 回读真实 schema（SQLAlchemy inspect()），反写 DataMason 元数据：
  │     table_specs 存「以数据库为准」的列清单（类型/是否 null/comment）
  │
  ├─⑤b 页面清单生成（DR-07，确定性映射）：table_spec → page_specs。
  │     页面（不是表）是界面层的产出单位，部署提案里给用户看的"访客留言页 + 后台管理页"
  │     就是它：kind ∈ { crud_list, public_form, dashboard }，access ∈ { public, member }。
  │     默认规则：每张表 → 1 张 crud_list（member）；提案可含 public_form（如留言提交页）。
  │     CRUD 引擎按 page_spec 渲染页面，而非按表裸出页面——页面与表是多对一关系。
  │
  └─⑥ 生成即提案：整条链路只产生「提案卡」数据，用户确认后才落库执行
         确认后：真建表 + 生成页面清单（page_specs）+ 生成 CRUD 配置（见第五节）
```

**保证外键规范的关键**（产品一页纸的 80% 一次通过率指标）：
1. 规格 schema 层强制「主外键与关联规范」——LLM 的自由度被 schema 约束，不可能生成无主键表；
2. 生成后自检：主键存在、外键有引用目标、类型方言合法——自检失败回喂重试；
3. 物理建表后回读 schema 与规格比对，不一致告警但不阻断（以数据库为准）。

**对齐文件**：`table_spec.py`（= chart_spec.py）、`ddl_builder.py`（= form_data_builder.py）、`deploy_jobs.py`（= dashboard_jobs.py）、`models.py`。

### 五、核心机制二：元数据驱动的 CRUD 引擎（数据库直转 CRUD）

#### 5.1 外部方案调研结论

「数据库 schema → CRUD」的开源生态分四类，逐一评估：

| 方案 | 形态 | 与 DataMason 的适配性 |
|---|---|---|
| **PostgREST / Hasura** | PG schema → REST API（无 UI） | 仅 PG，且无界面半成品；**借鉴其 API 语义**（`/tables/{name}/rows`、过滤/排序/分页参数） |
| **NocoDB / NocoBase / Baserow** | schema → 低代码表格 CRUD UI | 完整成熟产品，但自成体系（各自的大前端 + 私有元模型），与 superset-lite 栈不一致，**不可嵌入**；**借鉴其表格交互**（过滤条/行内编辑/视图模式） |
| **Flask-Restless / Flask-Muck** | SQLAlchemy model → CRUD REST | 需静态 model 类，反射支持弱；Flask-Restless 已停止维护，Flask-Muck 维护一般。**不引** |
| **SQLAlchemy automap + 自研 router** | 反射 schema → 动态模型 + 动态路由 | 与 superset-lite 栈完全同构，零重依赖。**作为自研底座** |
| 其他（refine / DB2OpenAPI / ServiceStack AutoQuery） | 前端框架 / OpenAPI 生成 / .NET | 栈不对齐，仅作概念参考 |

#### 5.2 选型结论：自研「元数据驱动」通用 CRUD

不为每张表生成代码（那是传统代码生成器，部署慢、难改），而是**生成「CRUD 配置」，由通用引擎解释执行**——与 superset 的「dataset 元数据 + chart 插件渲染」同构：

```
部署确认后（第四节第⑥步产出）：
  table_spec ──确定性映射──► 四份产物：
                             ① DDL（已执行）
                             ② 页面清单 page_specs（DR-07）
                             ③ CRUD API 配置  crud_spec_payload
                             ④ CRUD UI 配置   crud_ui_config
```

**API 层**（Flask 动态蓝图，按 deployment 挂载到 `/app/{deployment_id}/api/`）：
- 通用路由：`GET /tables/{name}/rows`（分页/排序/过滤/搜索，PostgREST 风格参数）、`GET /tables/{name}/rows/{pk}`、`POST /tables/{name}/rows`、`PUT .../{pk}`、`DELETE .../{pk}`、`GET /meta`（前端渲染元数据）。
- 引擎实现：SQLAlchemy 2.x 反射（`MetaData.reflect()` 限定表）→ 动态构造 `Table` 对象 → 单表 CRUD + 外键自动转「关联下拉」数据（`GET /tables/{name}/refs/{fk_col}`）。
- **安全**：列白名单（只暴露 ui_config 允许的列）、参数化查询、行级「我的记录」过滤（v0.2 文档要求的操作员数据级权限）。

**UI 层**（React + antd 通用组件，元数据驱动渲染，零代码生成）：
- 列表页：列显示集、搜索字段、外键列转 tag/下拉、操作列（编辑/删除/详情）——配置即渲染；
- 表单页：字段控件类型映射（text/number/date/select(外键)/textarea）、必填/唯一/长度校验、关联下拉——配置即渲染；
- 表格交互细节（排序、过滤条、导出 CSV）参考 DBX 数据表格（第三节）；
- 浏览模式（P0）：纯网格 + 简单筛选，不带编辑（对齐 MVP 范围）。

**为什么这是正确答案**：
1. 与 superset-lite「LLM→规格→确定性映射」哲学同构，团队心智模型统一；
2. 无重依赖、无代码生成，schema 变更后刷新元数据即可；
3. 运行时 CRUD 直连目标库（SQLAlchemy 直连，不走第三方工具中转），性能可控；
4. NocoDB/PostgREST/DBX 的成熟交互作为 spec 输入，站在巨人肩膀上自研薄引擎。

**操作日志挂在写路径上（P1，固定能力）**：
- 通用 router 的 `POST/PUT/DELETE` 是唯一业务写入口——在引擎层统一挂写入钩子写 `activity_logs`，不为每张表做任何配置（元数据驱动，日志也是）。
- `create/update/delete` 三种动作：UPDATE 在执行前按主键读出旧行，提交后只把**变更字段的 `{旧值 → 新值}`** 存入 `changes`（JSON），未改字段不进日志，控制体积；DELETE 存主键 + ui_config 选出的业务标签（object_label，如"退货单 #88 · 破损 2 件"），保证记录没了日志仍读得懂。
- 取值经 ui_config 列白名单与控件类型格式化（外键存显示值而非裸 id），大字段/二进制截断。
- **两阶段写入 + 启动对账（DR-03）**：业务写在部署的独立物理库、日志在元数据库，两库**无共享事务**——不做任何跨库原子性承诺。固定顺序：① 元数据库写 `status=pending` 日志 → ② 业务写提交 → ③ 日志置 `status=committed`。②失败则删除①（业务报错、无日志）；③因进程崩溃缺席时由**启动对账任务**收尾：pending 超时 → 回查该业务动作是否已生效（新增/删除查主键存在性、修改查目标值），生效则 finalize，未生效则丢弃。日志可靠性由「对账」保证，代码注释与运维文档统一按此表述。
- 查询侧：`GET /app/{id}/api/activity-logs` 支持 actor/object_table/action/时间区间过滤 + 倒序分页；权限复用三层角色——creator/admin 看全部，operator 强制 `actor_user_id = 自己`。记录详情的"操作记录"走同接口按 `(object_table, object_pk)` 过滤。日志只追加，不提供任何 update/delete 路由。
- 系统动作（deploy/stop/start/destroy/member/structure）由部署管线、成员服务、DDL 执行处各自写入，`actor_user_id` 为 NULL 表示系统。日志随部署生灭：停止不动，销毁时随元数据一并清除；P2 导出包包含 activity_logs。

**边界（MVP 明确不做）**：多表联动事务表单、计算列、复杂校验脚本；只读浏览/查询不记日志、不做行为监控。多表联动/流程以「流程规格」扩展，v0 归 M3（见 §八 flow_specs）。

### 六、核心机制三：部署生命周期（一验证一部署）

```
部署清单(首页)
  → [+ 部署一套系统] → 一句话 + 数据模式选择（从零建 / 接已有的[M2 起开放]）
  → 提案卡（表规格 + 页面清单 + 演示数据开关，可改可弃）→ 确认
  → 部署管线（状态可见，秒级）：
      建库 → 建表(DDL executor) → 回读 schema → 生成页面与 CRUD 配置
      → 演示种子数据（可关，DR-08）→ 注册运行时（/app/{deploy_id}/ 挂载点 + 工作台菜单）→ 就绪
  → ✔ 就绪：入口 {host}/app/{deploy_id}  [打开][演示][停止][销毁]
```

**两种数据模式**：
- **创建模式（MVP，M1）**：部署时经 `connections` 选定目标（本地 SQLite 文件 / MySQL / PG 独立 schema）→ 建库 → 按 table_spec 建表。
- **直连模式（接已有数据，M2/DR-09）**：选 DataMason 已有连接 → 读取 schema（全部或选定表）→ **反向生成 table_spec**（自动）+ AI 补齐业务标签（可选）→ 生成 CRUD 配置。反向链路 = superset「添加已有表为 dataset」的翻版，风险点在 schema 上下文过大，需两段式选表（迁移 superset 的 `_select_relevant_tables`）。MVP 期部署流只显示「从零建」，「接已有的」置灰并提示"下阶段开放"。

**演示种子数据（DR-08）**：为兑现"带真实数据就绪"（P5 原则），部署管线在建表后、就绪前生成演示数据——M0/M1 用**确定性生成器**（每表 8~12 行，外键值取自引用表已生成行，人名/商品名等从内置语料取值，不用 LLM、零成本可复现）；P1 起可由 LLM 生成更逼真的业务数据（走 ai_generations 埋点）。提案页提供"不要演示数据"开关；工作台设置里有"一键清空演示数据"（清空=按标记删除种子行，不影响后续真实录入）。

**状态机**：`draft → deploying → running → stopped → destroyed`（对齐 v0.2 文案：停止=保留数据可再启，销毁=数据一并清，销毁前给导出机会）。**草稿态定义（DR-13）**：部署流进行到「提案未确认」即为草稿——只存在于会话内，不落元数据库、不进清单、离开即弃；确认瞬间转 deploying。**演示不是状态**（是运行态下的视图模式）。

**技术形态决策**：
- 单 DataMason 进程承载多套部署（每套 = 元数据行 + 动态蓝图 + 前端挂载点 + 独立物理库）——部署动作是**注册入口**，不是起服务；
- 数据隔离：创建模式默认独立 SQLite 文件（或独立 schema）；直连模式指向已配置连接管理的库；
- 入口隔离：`/app/{deploy_id}/` 路由命名空间；P2 起支持自定义路径（留言板 → /guestbook）；
- **网络可达性（DR-17）**：MVP 定位**单机/局域网**——入口地址显示部署主机实际 IP（如 `http://192.168.x.x:port/app/guestbook`），不写死 datamason.local；异地演示由用户自行内网穿透；公网部署不做，P2 再评估；
- 强隔离（独立进程/容器）留 P2 可选项——但 **DBX 的 Docker 形态不再作为依赖**，若需要由 DataMason 自己做容器化。

### 七、核心机制四：工作台运行时 + 问数据 + 权限

- **工作台运行时**：`/app/{deploy_id}/` 由 left menu（部署时生成的菜单树）+ 内容区（CRUD 页面 / 数据视图）组成，纯前端组件复用「元数据驱动 CRUD」；演示模式一键隐藏构建痕迹（对齐体验文档 5.5）。
- **问数据（P3）**：右上角入口 → LLM 生成 SQL（继承 superset-lite generate_sql 设计，含只读门与自检）→ 数据层执行 → 视图卡（一句话结论 + 表格/图表 + 可展开 SQL）→ 可钉住成常驻报表。
  - **图表方案（已定，2026-09-15）**：自绘 ECharts（规格驱动，轻量同构），**不联动 superset-lite**；视图卡自带的图表规格由 LLM/确定性映射产出，前端通用组件渲染。
- **权限（P1 必做）**：
  - 元数据层：`users`（DR-10，全局用户表）+ `deployment_members`（deployment_id, user_id, role）；三层角色 per-deployment。**角色只定档位**：creator/admin = 全量功能；operator = 自己被授权的菜单集合（见下一条）。
  - 功能级裁剪（DR-02，**按人存储**）：权限配置 = 「把菜单分给人」（v0.2 交互），存储为 `deployment_menu_grants(menu_id, user_id)`——因为两个操作员的菜单可以不同（小李：入库单+库存查询；小张：质检单+退货处理），菜单→角色的映射表达不了这一点。后端按授权集合过滤菜单与路由。
  - 数据级：操作员默认只见「我的记录」（`WHERE created_by = 当前用户`，物理前提见 §四 归属列注入 DR-05），全量归创建人/管理员；直连表缺归属列时降级并明示。
  - **访客（DR-04）**：`page_specs.access=public` 的页面（如访客留言页）匿名可访问——访客**不是成员角色**，是"访问者"一类，仅能提交到公开表单、看不到任何菜单与数据；成员角色体系不变。分享=定板支持：MVP 入口仅本机/局域网可见，分享链接绑定身份 P2。
  - 认证 MVP 从简：本地用户表 + 会话（自建轻量会话，参考 FAB 思路但不引 FAB）；**首次启动向导（DR-10）**：M0 用环境变量（管理员账号 + LLM 端点/key/模型）完成初始化，M1 起提供设置页（管理员账号、LLM 配置、连接管理）——否则"输入对方账号添加成员"和 LLM 网关都无从谈起。

### 八、数据模型（元数据库，全部惰性建表）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | id, username, display_name, password_hash, is_platform_admin, created_at | 全局用户表（DR-10）；首个账号由首次启动向导创建 |
| `connections` | id, name, dialect(sqlite/mysql/postgresql), conn_uri(加密), status, created_at | 连接管理（自研数据层入口）；创建模式创建的本地库也在此登记 |
| `deployments` | id, biz_name, purpose, data_mode(create/link), connection_id, db_name/db_schema, status, entry_path, owner_id, seed_data(bool), created_at | 一套部署一行；seed_data 记录是否带演示数据（DR-08） |

| `page_specs` | id, deployment_id, kind(crud_list/public_form/dashboard), access(public/member), table_id, title, layout(JSON) | **页面**规格（DR-07）——提案里"访客留言页/后台管理页"的实体；页面与表多对一，公开表单页驱动访客提交 |

| `deployment_menu_grants` | menu_id, user_id | **按人授权**（DR-02）：菜单→用户的授权集合；操作员可见菜单=自己的授权；创建人/管理员全量无需授权行 |
| `deployment_members` | deployment_id, user_id, role(creator/admin/operator) | 三层角色（只定档位） |
| `flow_specs` | id, deployment_id, name, steps(JSON: 每步=页面引用+完成条件+状态字段), version | **流程规格 v0**（DR-06）：向导式流程（按步骤引导用户依次完成页面操作并推进状态字段），不做工作流引擎；M3 交付 |

| `llm_models` | 移植 superset `models/llm.py` | api_key 加密存储 |

建表方式：`Model.__table__.create(bind=conn, checkfirst=True)`，启动时/首次使用前惰性建——与 superset-lite 验证过的 `AiGeneration` 完全一致，不引 alembic。

> **元数据关联闭环（合并时补，防开发断档）**：`deployment_menus.ref_id` 统一指向 `page_specs.id`（菜单点击即渲染对应页面）；`flow_specs.steps[].页面引用` 同样指向 `page_specs.id`；部署确认后按默认规则自动生成「页面→菜单」映射（每张 `crud_list` 自动挂一个菜单项）。业务表 `created_by/updated_by` 存 `users.id`（bigint，NOT NULL DEFAULT 当前会话用户 id），「我的记录」= `WHERE created_by = 当前会话 users.id`，跨库靠 `users.id` 全局唯一对齐。

### 十一、风险与开放问题

| 风险/问题 | 说明 | 缓解/决策点 |
|---|---|---|
| **方言差异在真实库的坑** | MySQL/PG 的 DDL 细节（auto_increment/serial、类型映射、外键约束命名）在小表场景也有差异 | M0 用真库（不是纯内存）冒烟；ddl_builder 三方言分支用离线 pytest 逐类型覆盖（对齐 superset-lite 的 chart 契约测试手法） |
| 连接串与凭证安全 | MySQL/PG 直连涉及账号密码 | 存 `connections` 表加密（参考 superset Database 的加密存储），密钥本地配置；MVP 本地单机场景风险可控 |
| LLM 建表一次通过率 ≥80% | 外键规范 + 多表关联是最大不确定 | 规格 schema 强约束 + 生成后自检回喂重试；通过率指标以老猫真实场景为标尺 |
| 逻辑隔离 vs 进程隔离 | 敏感数据演示场景可能要求强隔离 | MVP 物理库隔离（数据层面安全）；进程/Docker 级隔离留 P2，需求明确再投入 |
| CRUD 引擎能力边界 | 复杂业务（多表联动/计算/流程）超出 MVP | M2 只做单表 CRUD + 外键下拉 + 我的记录；流程以向导式 flow_specs v0 落 M3（DR-06），多表联动事务表单仍不做 |
| 图表链路（已定） | ~~自绘 ECharts vs 联动 superset-lite~~ | 决策：自绘 ECharts，不联动 superset-lite（2026-09-15）；保持单一轻量技术栈 |
| 桌面 vs 浏览器形态（已定） | 本地库偏桌面、演示分发偏 Web | 决策：**只做 Web 版**（2026-09-15）；本地 SQLite 由 Web 服务端进程管理，不做 Tauri 桌面壳 |
| 参考项目的能力边界 | DBX 的 Redis/MQ/专项能力超出产品范围 | 明确不做，保持「验证型信息系统」的产品边界 |
| 网络可达性（DR-17） | 演示分发隐含"别人如何访问"，无人交代 | MVP 定位单机/局域网：入口显示部署主机实际地址；异地演示用户自行内网穿透；公网不做，P2 评估 |
| superset-lite 移植可得性（DR-18） | 移植清单引用其内部实现，前提是 0.2.0 源码可得 | 开工前确认源码可得；任一资产不可得按 §〇 移植清单的能力契约自实现，里程碑不变 |
| 日志对账窗口（DR-03） | 两阶段写入在进程崩溃时留下 pending 日志 | 启动对账任务回查生效性收尾；对账前 pending 行不进日志页查询结果 |
