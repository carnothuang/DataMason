# DataMason 规划文档走查报告（可实施性视角）

> 走查时间：2026-09-15 ｜ 视角：高级开发工程师（开工前技术落地审查）
> 走查对象：5 份规划文档（产品一页纸 v0.2 / 设计细化 v0.2.1 / 体验设计细化 v0.2.1 / 技术路线 v0.2.1 / 决策记录 v0.2.1）
> 目的：**在 M0 开工前，找出会导致后续开发断档、返工、理解偏差的不足与前后逻辑差异。**
> 定位说明：决策记录 v0.2.1 已解决 18 项「文档一致性」矛盾；本走查在其之上，专门审「**技术模型能否落地**」这一被 DR 走查忽略的维度。

## 〇、总体结论

文档整体质量高：产品方向清晰、架构分层合理、DBX/superset-lite 的参考边界划得干净、DR 裁决机制（决策先行 + 编号权威 + 术语固定）能有效防止再断档。

**但是**，DR 走查主要收敛的是「口径/措辞矛盾」，没有覆盖「**工程实现是否闭环**」。本次在 DR 修订后仍发现 **5 项阻塞级断档（B 类，不解决就会卡开发）**、**10 项中危不一致（C 类，会返工/理解偏差）**、**4 项轻微噪音（D 类）**。其中 B 类多数集中在「元数据模型缺关联定义」和「部署流 UX 闭环缺失」两块——这正是 DR 走查没碰的地方。

**建议**：M0 开工前，把 B 类 5 项以新 DR 条目（DR-19~）固化，并补一次「技术模型可落地性」专项走查。

## 二、阻塞级断档（B 类，必须解决，否则开发直接卡住）

### B1 ｜ M1 创建模式部署缺少「目标库连接」的建立环节
- **位置**：技术路线 §六（创建模式"经 connections 选定目标"）、§八（connections 表）、§十 M1（"连接管理（收敛版）"）；体验 UI-4（"连接管理（只读连接状态 + 切换）"）；DR-09（MVP 部署流只显示「从零建」）。
- **现象**：创建模式部署流第一步（设计 §三 / 体验 §4.5）只有「一句话 + ●从零建 ○接已有的」，**没有连接选择/创建步骤**；而 M1 的「连接管理」被明确为**只读**。也就是说：M1 创建部署需要连接，但连接管理在 M1 不能写、部署流又不建连接——连接从哪来成悬空。
- **影响**：M1 验收「描述→提案→确认→建表→带演示数据→浏览」的闭环在第一步就断：开发者不知道「从零建」的 SQLite 文件 / MySQL / PG schema 在哪建立、连接如何登记进 `connections` 表。
- **建议**：
  1. 明确 M1 创建模式的连接建立路径二选一：① 部署流第一步扩展为「选/建目标库」（SQLite 自动生成路径如 `deployments.db_name` 决定文件名；MySQL/PG 填连接参数并登记到 `connections`）；② 或把连接管理的「创建」能力在 M1 就开放（仅服务创建模式）。
  2. 定义「从零建」的 SQLite 默认路径生成规则，写入技术路线 §六。
  3. 在 DR-09 补一句：MVP「只读连接管理」仅指**直连模式**的连接，创建模式的连接在部署流内隐式建立。

### B2 ｜ `deployment_menus` 与 `page_specs` / `flow_specs` 之间无关联定义
- **位置**：技术路线 §八（`deployment_menus` 字段 `kind(table/flow/dashboard), ref_id`、`page_specs` 字段 `table_id`；§五 页面与表多对一）。
- **现象**：菜单项 `kind` 有 table/flow/dashboard，`ref_id` 指向未定义；`page_specs` 是页面实体（crud_list/public_form/dashboard），但**没有任何字段/说明把「菜单项」关联到「page_specs」**。菜单点击后渲染哪个页面？`menu.ref_id` 指向 `table_specs` 还是 `page_specs`？`flow_specs.steps` 的「页面引用」又是 `page_specs.id` 还是 `menu.id`？全未定义。
- **影响**：后端建模（菜单树怎么存）和前端渲染（点菜单出哪个页面）都无据可依，M2 菜单组装 / M3 流程向导会同时卡住。这是元数据模型的结构性缺口。
- **建议**：
  1. `deployment_menus` 增加 `page_spec_id`（或明确 `ref_id` 统一指向 `page_specs.id`，`kind` 仅作渲染提示）。
  2. `flow_specs.steps` 的「页面引用」明确 = `page_specs.id`。
  3. 定义「部署确认后默认页面→菜单」的自动生成规则（如每张 `crud_list` 自动挂一个菜单项），写入 §四 ⑤b / §八。
  4. 明确 `menu.kind=dashboard` 时 `ref_id` 指向 `page_specs(id, kind=dashboard)`。

### B3 ｜ MVP 提案卡「逐张修改」无落点界面
- **位置**：体验 §5.2（提案卡按钮含「逐张修改」，定义为"点开即进入蓝图的单表编辑"）；体验 §七（"数据蓝图（业务化 ER + 单表编辑）"标 M2(P1)）；技术路线 §十 M1 验收（"提案卡在 M1 即可用，**验收不依赖 M2 交付物**"）。
- **现象**：M1 提案卡有「逐张修改」按钮，但其目标界面（蓝图单表编辑）M2 才交付。技术路线明确 M1 不依赖 M2，体验却把逐张修改定义为"进蓝图单表编辑"——两者冲突。
- **影响**：M1 前端不知道「逐张修改」点了去哪；若硬等 M2 蓝图，M1 验收不成立。
- **建议**：统一措辞——MVP 的「逐张修改」= **在提案卡内直接做字段级编辑（改 table_spec 草稿）**，不进入可视化蓝图；蓝图单表编辑（ER + 拖拽）仍是 M2。改体验 §5.2 与 §七 对应表述。

### B4 ｜ 用户身份跨库对齐未定义（业务表 `created_by` vs 元数据库 `users.id`）
- **位置**：技术路线 §四 ②b（创建模式强制注入 `created_by/created_at/updated_by/updated_at`）；§七（"我的记录" = `WHERE created_by = 当前用户`）；§八（`users` 全局表在元数据库、`activity_logs.actor_user_id` = `users.id`）。
- **现象**：业务表在部署的独立物理库，`created_by` 存什么（id 还是 username）未定义；「当前用户」是 `users.id` 还是 `username` 未定义。元数据库用 `users.id` 标识身份，业务库用 `created_by` 列——两库如何对齐成同一身份没说。
- **影响**：P1「我的记录」过滤、`activity_logs` 与业务记录的关联查询会出错或无法 JOIN。
- **建议**：约定 `created_by/updated_by` 存 `users.id`（bigint，NOT NULL DEFAULT 当前会话用户 id），`created_at/updated_at` 存时间戳；「我的记录」= `WHERE created_by = 当前会话 users.id`。跨库靠 `users.id` 全局唯一对齐。补到 §四 ②b 与 §七。

### B5 ｜ DR-01 里程碑编号措辞错配（M0–M4 = P0→P3 是 5 对 4）
- **位置**：决策记录 DR-01（"技术路线 M0–M4 为唯一权威（=P0→P3）"）；技术路线 §十（M0 技术验证 / M1=MVP(P0) / M2(P1) / M3(P2) / M4(P3)）。
- **现象**：M0 是 P0 **之前**的技术验证里程碑，不对应任何产品阶段；但 DR-01 写成 M0–M4 = P0→P3，等于说 M0 就是 P0 起点。产品一页纸 §七 实际是 M1=P0、M2=P1、M3=P2、M4=P3（M0 无 P 映射）。
- **影响**：排期/沟通时新人会误以为 M0 即 P0，导致 M0 技术验证被当成产品 MVP 起点，范围与验收理解混乱。
- **建议**：DR-01 改为——「技术路线 **M1–M4** 对应产品 **P0–P3**；**M0 为独立技术验证里程碑**，不对应任何产品阶段」。同步核对四份文档中一切把 M0 当产品起点的暗示。

## 三、中危不一致（C 类，会返工或理解偏差）

### C1 ｜ 部署卡按钮两份文档不一致
- 设计细化 §二 线框图：`[打开][演示][停止][销毁]`（**无分享**）；体验 §4.4：`[打开][演示][分享][停止][销毁]`（**有分享**）。
- 影响：UI 实现时卡片按钮以谁为准。DR-04 已定板分享，应以体验 §4.4 为权威。
- 建议：设计细化 §二 线框图补 `[分享]`，或在文档注明"以体验设计细化 §4.4 为权威"。

### C2 ｜ 产品一页纸缺失「首次启动向导 / LLM 配置」前置
- 技术路线 DR-10 明确「无 LLM 配置则全产品无法工作」，M0 环境变量 / M1 设置页是硬前置；但产品一页纸（外部沟通基线）§七 MVP 范围**完全没提初始化/配置**。
- 影响：对外演示时用户会问"我怎么填 LLM key"，方向文档无答案。
- 建议：产品一页纸 §七 或新增小节补「初始化与配置（首次启动向导：管理员账号 + LLM 端点/key/模型，无配置无法部署）」。

### C3 ｜ 产品一页纸六大能力列表与阶段表口径冲突
- 能力 #3「引用生成…可视化交互界面…（P2）」把界面生成标 P2，但 MVP 有「表数据浏览」、M2 有完整 CRUD——暗示界面是 P2 才做，与范围表冲突。
- 能力 #6「AI 伴随全程…在工作台直接询问进度、数据反馈结果」未标阶段，像 MVP 核心能力，但问答实为 P3(M4)。
- 建议：能力 #3 改为「MVP 只读浏览 / M2 完整 CRUD」；能力 #6 注明「问答为 P3(M4)，MVP 仅建表/建界面伴随」。

### C4 ｜ 部署流步骤线框图缺「回读 schema」
- 设计细化 §三：`建库 → 建表 → 生成页面 → 演示数据 → 注册入口`（**无回读**）；技术路线 §六 / 体验 §4.5：含「回读 schema」。
- 建议：设计细化 §三 线框图补「回读 schema」步，三处统一。

### C5 ｜ MVP 期 `[分享]` 按钮行为未定义
- 体验 §4.4：MVP「分享链接绑定身份 M3(P2) 实现」，但 MVP 卡片已有 `[分享]` 按钮。
- 影响：MVP 点分享干嘛？复制本机 URL？还是禁用？未定义。
- 建议：明确 MVP `[分享]` = 复制当前本机/局域网入口 URL（无身份绑定、无访客页）；身份绑定与访客页 M3 才交付。

### C6 ｜ 命令层「Excel 导入」联想词出现在 MVP 前
- 体验 §5.1 命令层联想示例含「我有一张 Excel 表，帮我导进来」；但 DR-16 明确 Excel 导入是 P2+ 备选、不绑定里程碑。
- 影响：MVP 展示该联想词会引导用户点尚不能用的功能，制造"承诺未实现"的信任落差。
- 建议：MVP/早期移除该联想词，或标注「下阶段开放」。

### C7 ｜ `page_specs` 的 `dashboard` kind 来源未定义
- §四 ⑤b 列出 `kind ∈ {crud_list, public_form, dashboard}`，但全文未说 dashboard 页面由谁、何时生成（部署自动？P3 钉住报表写入？）。
- 建议：在 §四 ⑤b 定义 dashboard 页面来源（如 P3 钉住报表写入 `page_specs(kind=dashboard)`，或部署不自动生成 dashboard）。

### C8 ｜ 平台管理员（`is_platform_admin`）职责与多部署关系未定义
- §八 `users` 有 `is_platform_admin`，但部署角色是 per-deployment（creator/admin/operator）。平台管理员是否跨部署可见、能否进他人部署、能否管全局，全未定义。
- 建议：补充平台管理员职责边界（建议：仅首账号 + 全局运维视角，不自动获得他人部署权限），写入 §七/§八。

### C9 ｜ 认证表述矛盾（「对齐 FAB」 vs 「自建 users + 会话」）
- §七：「认证 MVP 从简：本地用户表 + 会话（**对齐 superset FAB** 的轻量用法）」；§二 选型只列 Flask 3.x，未引 FAB。
- 影响：开发者会犹豫到底引不引 Flask-AppBuilder。
- 建议：统一为「自建轻量会话（参考 FAB 思路，不引 FAB）」，去掉「对齐 superset FAB」歧义。

### C10 ｜ 销毁后元数据留存与「告别态」界面未定义
- DR-13 / §八：销毁=数据一并清；§五「销毁时随元数据一并清除」；但体验 §6.4「已销毁：不进列表，仅留导出提示后的告别态」。
- 现象：`deployments` 行销毁后删否？「告别态」界面数据从哪来？未定义。
- 建议：明确销毁时 `deployments` 行标记 `status=destroyed` 并隐藏，导出提示关闭后物理删除（或软删）；定义「告别态」只在使用者刚点销毁、导出弹窗期间存在，不持久。

## 四、轻微噪音（D 类，不影响落地，建议顺手修）

- **D1** 表名不一致：§〇 称 `LlmModel`，§八 写 `llm_models`。统一为表名 `llm_models`（类 `LlmModel`）。
- **D2** §九 目录树未列 `table_spec.py` 模块位置（§四 末尾引用了"对齐文件 table_spec.py"），建议补到 `server/meta/` 或 `server/llm/`。
- **D3** §八 `table_specs.status` 仅列 `(applied/...)`，与「提案留痕 / 草稿态仅会话内」表述轻微冲突；建议补 `draft` 或注释"提案态不落此表"。

## 六、元建议（防再断档的机制层面）

决策记录 §四 的维护规则很好，但本次走查暴露一个规律：**DR 走查是「文档一致性走查」，不是「可实施性走查」**。18 项 DR 解决了矛盾，却没发现 B1–B5 这类「模型能落地吗」的问题。

建议：
- 在 DR 维护规则中追加一类触发条件——**「任何涉及元数据模型新增/变更、部署流 UX 闭环、跨库身份」的改动，除 DR 条目外，必须附「实现闭环说明」（表间关联、接口契约、UX 步骤）**。
- M0 开工前，以新 DR 条目（DR-19~）固化本报告 B 类 5 项，并做一次「技术模型可落地性」专项走查（重点审：元数据 FK 关联、REST 接口契约、部署流每一步的落库动作）。

*本文件为规划文档的可实施性走查产物，不与四份规划文档冲突，仅作为开工前补充审查。如发现新的跨文档决策，按《决策记录 v0.2.1》§四 规则追加 DR 条目。*
