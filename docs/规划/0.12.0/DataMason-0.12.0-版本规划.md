## 一、为什么是这件事

0.11.0 把系统做「大」、做「全」、做「分得清」之后，0.12.0 把目光放回**起点**——用户第一次点「部署一套系统」的那一步。

### 1.1 现状：一句话 → 全自动，一步到位

当前创建模式（数据从零建）的链路（`src/datamason/deploy/service.py::preview/confirm` + `dashboard/src/pages/deploy/DeployWizard.tsx`）：

```
一句话描述 → LLM 一次生成完整 table_spec（表+字段+关系+页面）→ 只读提案卡 → 就这么部署
```

### 1.2 真实缺口：全自动的「一锤子」在复杂需求上失灵

| # | 现象（测试观察） | 根因 |
|---|---|---|
| 1 | **简单需求很顺，复杂系统拉胯**：一次让 LLM 产出"几十列 × 多表 × 关系"的完整规格，表多字段多时结构自检常反复失败，或产出的字段/关系跑偏 | 一步到位 = 把「表结构设计」「字段设计」「关系设计」三个决策绑在一次调用里，失败面大、不可分步纠偏 |
| 2 | **生成完只能"要么接受、要么重来"**：提案卡只读，改一处字段/关系只能退回重写描述重生成；「调整一下」回到输入页 = 前面的生成全部作废 | 中间结果没有编辑能力 |
| 3 | **用户失去掌控感**：复杂系统用户其实有很强的领域判断（"这两张表不该关联""金额字段要小数"），但当前流程没有给用户在任何一层「确认/修改」的机会，只有最后一步全量确认 | 缺少人机协作的决策点 |

### 1.3 0.12.0 的回答：混合模式（NL 分步引导 + 可视化确认）

> **混合模式**：自然语言仍是主引导，但拆成**两段**——
> **第一段只谈"几张表、表与表的关系"**（表级骨架），生成后**不落案**，以**表关系图示**呈现给用户确定；
> **第二段再由用户用 NL 逐表引导字段内容**，字段实时渲染到同一张图示上；
> **全程支持用户修改表、关系与字段**，最终确认后走既有落库链路。

一句话：**全自动解决"能跑"，混合模式解决"跑得对"**。这延续了产品一贯的「生成即提案，确认才落库」哲学，并把决策点从"最后一步"前移到"每一层"。

## 二、版本范围与边界

### 2.1 范围内（M6 单轨）

| 轨 | 能力 | 一句话 | 主要使用角色 |
|---|---|---|---|
| **M6 混合建库** | 创建模式下「一句话 → 表骨架图示确认 → 逐表 NL 字段 → 全量确认落库」，全程可视化可编辑 | 复杂系统分两步长出来，每一步都有人的确认 | 创建人（工程室） |

### 2.2 明确不做（边界）

- **直连（link）模式不开放混合建库**：外部库是"反向反射已有结构"，语义是"接进来"而非"建出来"，维持 DR-27 只读红线；混合模式只对创建模式（DataMason 自建库）开放。
- **不引入图数据库 / 力导向布局库 / ReactFlow 等新前端依赖**：交互式 ER 画布在现有 `ErGraph` 基础上自研受限版本（环形/网格布局 + 节点增删 + 连线编辑 + 字段展开），保持 0.11.0 的"前端零新增依赖"纪律。
- **草稿不做服务端持久化**：混合模式的中间态（表骨架 + 各表字段）在浏览器端内存维护，仅在最后确认时一次性提交完整 spec；刷新/关闭丢失（界面提示）。不做 draft 表、不做多人协作。
- **字段级 NL 只做「整表生成 / 追加字段」两种**：不做增量自然语言清洗 DSL、不做字段级智能改名建议的复杂语义。
- **多对多关系不直接建模**：骨架关系 v0 只表达"引用"（一对多/多对一），多对多沿用关系建模惯例由中间表承载（提示用户加关联表）。
- 沿用 0.11.x 边界：表重命名、跨表结构迁移、数据清洗规则引擎、工作流引擎、复杂行级权限等不做。

## 三、能力设计：混合建库（M6）

### 3.1 入口：与「全自动」并存，不替换

在部署向导（`DeployWizard`）创建模式的输入页，增加**模式选择**（Segmented，与"数据从零建/接已有的库"同级或作为 create 的子选项）：

| 模式 | 交互 | 适用 |
|---|---|---|
| **全自动**（现状，不动） | 一句话 → 完整提案 → 就这么部署 | 简单/验证型需求 |
| **混合·分步引导**（新增） | 一句话 → 表关系图示 → 逐表字段 → 全量确认 | 复杂/正式需求 |

### 3.2 四步流程

```
Step 1 意图 ── 一句话描述业务 + 系统名称（复用现有输入）
      │
Step 2 表骨架 ── NL → LLM 只产「表集合 + 表间关系」→ 交互式 ER 图示
      │          用户：增/删表、改表名与业务名、画线/删线（增删关系）→ 确认骨架
      │
Step 3 逐表字段 ── 选中表节点 → NL 引导该表字段 → 字段渲染到图示节点上
      │           用户：NL 可反复（整表重生成/追加字段）、手改字段（复用字段编辑交互）
      │           关系与字段双向联动（删线=删外键列，改外键列=图上连线变化）
      │
Step 4 确认落库 ── 骨架 + 各表字段合并为完整 SchemaSpec → 服务端强校验
                    → 复用既有 confirm 链路（建库/建表/页面/菜单/种子/入口）
```

### 3.3 Step 2 · 表骨架：只谈表与关系

**输入**：一句话业务描述（同 Step 1）。

**LLM 产出（表级骨架，新中间规格）**：不产字段（或仅主键占位），只产

```json
{
  "biz_notes": "整库做什么（一句话）",
  "tables": [
    {"name": "customers", "biz_name": "客户", "biz_notes": "客户档案"},
    {"name": "orders",    "biz_name": "订单", "biz_notes": "客户下的订单",
     "relations": [{"to_table": "customers", "note": "订单属于客户"}]}
  ]
}
```

**Python 确定性映射**（沿用「LLM 只产中间规格，Python 确定性映射」纪律）：
- 新 pydantic 模型 `SchemaSkeleton`（见 §三·6）强校验：表名唯一、表名合法、关系目标必须存在、禁止自环。
- `relations` → 外键列占位：在子表生成 `<目标表名>_id` 列（INTEGER，`ref_table`/`ref_column` 指向父表主键），列名冲突时追加语义后缀（如 `customer_id` → `related_customer_id`），由字段级阶段可再改。
- 每表先注入骨架主键 `id`（INTEGER 自增），归属列 `created_by/created_at/updated_by/updated_at` 仍由系统注入（DR-05），不占用用户视野。

**图示呈现**：交互式 ER 画布（见 §三·5）渲染表节点 + 关系连线，节点上显示「业务名 + 表名 + 字段数」，未做字段级时字段区为空态提示"待引导字段"。

**用户可做**：
- 增表（空白表节点，进入 Step 3 引导字段）
- 删表（画布上删节点；若被其他表引用则弹影响提示，需先删引用线——沿用 DR-31 保守哲学）
- 改表名 / 业务名（节点内编辑）
- **画线 = 新增关系**（弹层确认外键列名，默认 `<目标表>_id`；目标表必须是已存在表）
- **删线 = 删除关系**（确认后级联删除对应外键列）
- 确认骨架 → 进入 Step 3

### 3.4 Step 3 · 逐表字段：NL 引导 + 图上显示 + 可修改

**入口**：在画布上选中某张表节点（或节点上的"引导字段"按钮）。

**NL 引导（字段级生成，新 prompt）**：

- 输入 = 该表业务名/表名/业务描述 + **骨架上下文**（同部署内已存在的表清单，供外键引用）+
  用户对该表的自然语言描述（如"客户表要记姓名、电话、VIP 等级、入会时间"）。
- LLM 产出该表完整 `columns`（复用现有列规则与类型白名单，含 FILE 附件类型）；外键列只允许指向骨架内已存在表的**主键**。
- pydantic 强校验 + 失败回喂重试（沿用 `MAX_RETRY=2` 与 `_flatten_validation_error`）。
- 两种模式：`overwrite`（整表重生成，默认）与 `append`（追加字段，用于"再加一个备注字段"这类增量引导）。

**字段渲染到图示**：表节点随字段生成展开——节点内列出字段（业务名 + 类型 + 主键/外键/唯一标记），字段多时折叠为"前 N 个 + 共 N 列"，可展开。

**用户可修改（复用字段编辑交互）**：
- 字段行内编辑：字段名 / 业务名 / 类型 / 长度 / 可空 / 唯一 / 主键 / 外键目标（`FieldEditor` / `NewTableModal` 已有的行编辑交互平移过来）。
- 加字段 / 删字段。
- **关系联动**：改某列的外键目标 → 图上连线随之重画；删掉一个外键列 → 图上对应连线消失（单一数据源，见 §三·5）。

**未引导字段的表**：不允许进入 Step 4（或提示"表 X 还没有字段"），保证不会把空表落库。

### 3.5 交互式 ER 画布（前端核心，自研）

在只读 `ErGraph` 基础上扩展为可交互组件 `ErCanvas`（`dashboard/src/components/`）：

| 能力 | 说明 |
|---|---|
| 节点 | 表节点可增删、可改表名/业务名；节点内展开字段列表（业务名+类型+标记） |
| 连线 | 外键关系连线可增删；新增连线弹层定外键列名（默认 `<目标表>_id`）；连线箭头指向被引用表 |
| 布局 | 环形/网格确定性布局为基底（沿用现有算法），节点支持简单拖动微调（v0 不要求拖拽持久化到服务端，草稿态即可） |
| 联动 | **单一数据源 = 字段定义**：画布只是视图 + 编辑入口。所有关系/字段变更都写回前端草稿 state（`useReducer`），画布据此重渲染——关系与字段永不出现两套真相 |
| 状态 | 草稿（表集合 + 各表字段）全程在浏览器内存；最后合并为完整 spec 一次提交 |

### 3.6 中间规格与合并（后端）

**新增 pydantic 模型（`src/datamason/ddl/skeleton.py`）**：

```python
class RelationSpec(BaseModel):
    to_table: str          # 目标表（被引用表）
    note: str = ""         # 关系语义（如"订单属于客户"）

class SkeletonTable(BaseModel):
    name: str              # 表名（合法 snake_case，全局唯一）
    biz_name: str = ""
    biz_notes: str = ""
    relations: list[RelationSpec] = []   # 引用方向：本表 → 目标表

class SchemaSkeleton(BaseModel):
    biz_notes: str = ""
    tables: list[SkeletonTable]          # 非空
    # 校验：表名合法且唯一；关系目标必须存在于 tables；禁止自环
```

**合并器**（`merge_skeleton_columns(skeleton, columns_map) -> SchemaSpec`）：
- 输入：确认后的骨架 + `{table_name: [ColumnSpec, ...]}`（各表字段，主键 id 与归属列由系统补齐）。
- 输出：完整 `SchemaSpec`，再过一遍 `SchemaSpec._validate_structure`（单主键/无重名列/外键引用存在且指向主键/无孤儿表）。
- 校验失败 → 返回**可读错误清单**（定位到表/字段），前端回到画布对应节点修正，不整体失败重来。

### 3.7 落库：完全复用

合并出的完整 `spec_json` 直接走既有 `POST /deployments/confirm`（`src/datamason/deploy/service.py::confirm`），页面派生（`_derive_pages`）、演示种子、菜单注册、入口注册全部沿用——混合模式**只改"造 spec 的过程"，不改"落库的过程"**。

## 六、验收标准

**离线（pytest，每任务验收线）**
- 骨架：合法骨架通过；重名表、关系目标不存在、自环、空表集合各拒绝；relations→外键列映射确定且无重名；
- 字段级：overwrite/append 均合法；外键仅允许指向骨架内已存在表主键；悬空引用拒绝并回喂；未引导表不可落库；
- 合并：骨架+字段合并后完整过 `SchemaSpec` 校验（单主键/重名列/外键存在/无孤儿表）；校验失败返回可读错误清单；
- 落库：混合模式确认 == 全自动确认链路（同 `confirm`），无回归。

**真实浏览器（Playwright，里程碑验收线）**
- 描述"客户与订单（含回访记录）"→ 骨架图示出现三张表与关系连线；
- 画布上删一条线、加一条线（弹层定外键列名）→ 图与字段联动一致；
- 逐表 NL 引导字段 → 字段显示在对应节点上；改字段类型/外键目标 → 图上即时反映；
- 故意留一张表不引导字段 → 落库被拦截并提示；补上后部署成功 → 工作台菜单出现 → 可录数据；
- 直连模式不出现混合模式入口（红线）。

**版本级**：独立验收报告（`docs/验收/`，沿用既有格式），M6 验收线全绿。

## 八、风险与开放问题

| 风险 / 开放问题 | 说明 | 缓解 / 决策点 |
|---|---|---|
| **R1 两段一致性** | 用户确认骨架后又改关系，字段级生成的外键可能指向已删的表 | 合并时 `SchemaSpec` 强校验兜底 + 返回**可读错误定位**（回画布对应节点修正）；图上对被引用表删除给出影响提示 |
| **R2 画布交互复杂度** | 拖拽/连线/展开的交互细节多，自研可能工作量超预期 | v0 收敛：布局确定性（环形/网格）+ 节点可简单拖动；连线只做"点表到表 + 弹层定列名"，不做贝塞尔精细编辑；列为 M6-3 的第一优先验收 |
| **R3 LLM 字段质量** | 逐表 NL 仍可能产出不想要的字段 | overwrite 整表重生成 + append 追加 + 行内手改兜底；字段级也走重试回喂 |
| **R4 骨架关系歧义** | 多外键/双向关系/循环引用表达不清 | 强校验拦截（禁自环、目标必须存在）；多对多提示用户加中间表；关系语义列（`note`）仅作展示不参与 DDL |
| **R5 长流程中断** | 四步流程中途离开（刷新/关页）草稿丢失 | 界面明确提示"草稿在本地、关闭即失"；v0 接受（DR-37）；若高频反馈再评估草稿持久化 |
| **Q1（已确认）** | 混合模式入口形态 | **入口下拉二选一**：首页「部署一套系统」改为折叠下拉菜单，「全自动（简单业务）」走原一键流、「混合引导（复杂需求）」直达分步引导；弹窗支持最大化（2026-09-18 修订） |
| **Q2（已确认）** | 骨架阶段是否允许直接手建空表 | **允许**：画布"+ 新建表"→ 空白节点 → Step 3 引导字段，与 M5-A 增表体验一致（2026-09-18 定稿） |
