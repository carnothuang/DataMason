## 〇、设计的总纲

产品一页纸回答的是"**做什么**"——把想法一小时变成可运行、可交互、可查询的信息系统。
体验设计要回答的是"**用户凭什么敢信它**"。

DataMason 的核心体验命题不是"生成得有多快"，而是：

> **一个不懂技术的业务人，能否在十分钟内建立起"这系统是我砌的、我懂它、它能替我说话"的掌控感。**

一切设计决策围绕这个命题展开。

## 一、体验设计五原则

> **编号提示**：本节 P1–P5 指**设计原则**序号（原则一~五），与产品阶段 P0–P3 无关——文档中"原则 P5""P2 的实体化"均指本节编号。

### P1. 自然语言优先，但不剥夺控制权
- 对话是第一入口，**但对话不是唯一入口**。所有 AI 产出物都可以被直接操作、手工修正。
- 原则：**"说"用来创建，"手"用来微调**。创建靠自然语言，精修靠直接操作，两者随时切换。

### P2. 生成即提案（Generate = Proposal）
- 任何 AI 生成结果（表、界面、流程）都不是"直接写入"，而是以**提案卡**形式呈现：可看、可审、可改、可弃。
- 这是信任的根基：**AI 永远先给方案，用户永远保留最终裁决权**。

### P3. 一块一块砌，过程可见
- 呼应"瓦匠砌砖"：系统由一个个"砖块"（数据块、界面块、流程块）叠加而成。
- 每一个砖块在构建区里**看得见、进得来、动得了、拆得掉**。系统不是黑盒，是可见的墙。

### P4. 工程室与展厅，两个世界
- **工程室**（构建态）：AI 对话、表结构、提案卡都在这里，乱一点没关系，是干活的地方。**工程室入口为创建人独有**；管理员是"高级使用者"（全套功能 + 管理动作），操作员是"受限使用者"（只见被分配的菜单）。
- **展厅**（演示态）：一键切换，所有构建痕迹消失，只剩干净的运行界面与真实数据。
- 咨询场景的杀手锏：给客户看的永远是一个"已经做好的系统"，而不是"正在做的系统"。

### P5. 数据会说话
- 一切生成的界面默认**带着真实数据一起跑**，而不是空壳表单。
- 用户可以"边跑边问"：在工作台上直接提问，答案以数据视图而非代码形式回答。

## 二、三段式用户旅程：说 → 看 → 用（部署贯穿其间）

v0.2 的完整链路是：在**部署清单首页**发起一套部署 → 说 → 看 → 确认后秒级**部署就绪** → 用。「说/看/用」三段旅程发生在**一套部署内部**；「部署」就发生在「看」与「用」之间。

```
部署清单 [+ 部署一套系统]
   ↓
① 说（想法） ──► ② 看（蓝图） ──► 〔确认 → 秒级部署就绪〕 ──► ③ 用（运行）
   描述意图        审查与修正            建库/建表/出界面          运行+问答+迭代
   30 秒           3~5 分钟               进度可见                  持续使用
```

| 阶段 | 用户行为 | 系统/AI 行为 | 信任建立点 | 关键界面 |
|---|---|---|---|---|
| **发起** | 在首页点 `[+ 部署一套系统]`，一句话说要验证什么，并选「数据从零建」（「接已有的」MVP 期置灰，提示下阶段开放，DR-09） | 进入部署流，按数据模式准备（MVP：新建独立库） | 只有一个主按钮，不被选择淹没 | 部署清单 + 部署流第一步 |
| **① 说** | "帮我建一个进销存模型，管库存和采购" | 解析意图 → 生成**数据模型提案**（表 + 关联 + 中文业务说明） | 提案里"每一句中文说明"都看得懂 | AI 命令栏 + 提案卡 |
| **② 看** | 看关系图、点开表看字段、说"再加个供应商表" | 可视化 ER 图（业务化标注）→ 增量修改 → 确认落地 | 关系图让人看懂"订单-商品-品类" | 数据蓝图 |
| **部署** | 在提案卡点「就这么部署」 | 秒级管线：建库 → 建表 → 回读 → 生成页面与界面 → **演示数据** → 注册入口，进度可见 | 看见它真在干活，秒级拿到入口 | 部署进度 + 就绪卡 |
| **③ 用** | 点入口进界面、录数据、演示、问"上月退货率" | 工作台运行 → 数据问答返回视图 | 看到的是**带着真数据的系统**（就绪即含演示数据，可一键清空） | 工作台运行时 + 演示模式 |

**设计要点**：这些阶段不是互相跳转的工具，而是一套部署内部连续推进的状态（见第四节信息架构）。旅程**连续推进**，不允许出现"切换工具/换页面"的断裂感；部署完成后立刻给出可点开、可分享的入口，闭环"从说到跑"的最后一厘米。

## 三、核心交互模式：AI 伴随的三种形态

AI 不以"一个聊天窗口"存在，而以三种可切换的形态贯穿：

### 形态 A：指令层（Command）— 我说你做
- 位置：一套部署的构建器底部常驻命令栏（可快捷键唤出），不是霸屏聊天窗；「+ 部署一套系统」则是首页上的唯一主按钮。
- 时机：用户主动发起，如"建表""生成客户管理界面"。
- 产出：**提案卡**（见 P2），落进当前上下文区域。

### 形态 B：伴随层（Copilot）— 我看着我提示
- 时机：用户在数据蓝图或工作台浏览时，AI 在侧边给出**轻量建议**。
- 示例：用户在看库存表时，AI 提示"这张表缺'安全库存'字段，要加吗？"——一条可点击的小卡片，不打断主操作。
- 纪律：**建议默认折叠**，只露一行摘要；用户不点，就永远不打扰。

### 形态 C：问答层（Q&A）— 我问数据答
- 位置：工作台右上角的"问数据"入口。
- 行为：输入问题 → AI 生成查询并执行 → 返回**视图卡片**（数据表/图表 + 一句人话结论）。
- 图表由 DataMason **自绘 ECharts（规格驱动，已定不联动 superset-lite，2026-09-15）**：轻量同构，卡片级渲染，不引入外部看板。
- 关键：视图卡片可**钉住**到工作台上变成常驻报表；也可展开看"它查了什么"（SQL 按需披露，默认不吓人）。

**三种形态的关系**：A 负责建设，B 负责护航，C 负责运营。三者共享同一个上下文，但**绝不共用同一个窗口**——这是与"聊天机器人"产品的根本区别。

## 四、信息架构

### 4.1 两级信息架构

v0.2 是两个层级，而不是一棵"我的系统"树：

```
① 部署清单首页（Shell）
     │  唯一主按钮 [+ 部署一套系统]
     │  运行中的部署 · 已停止/历史（折叠）
     ↓ 点一张部署卡 / 点就绪入口
② 单套部署的工作台（/app/{部署标识}/）
     工程室：数据蓝图 · 界面 · 流程（构建态，创建人）
     展厅/运行：业务菜单 + 真实数据（使用态，全体成员按角色）
     两套态都自带：操作日志（固定件，见 4.7）
```

- **部署清单**回答"我部署过哪些系统"；**单套部署工作台**回答"这套系统长什么样、怎么用"。
- 每一套部署 = 独立数据 + 独立入口 + 独立成员，互不干扰——**折腾是安全的，因为隔离**。

### 4.2 单套部署工作台布局（Web，三栏 + 一条命令层；不做桌面端，2026-09-15 决策）

```
┌────────────────────────────────────────────────────────┐
│ ← 返回部署清单   留言板 · ● 运行中  【工程室/展厅】 问数据 │
├───────────┬───────────────────────────────┬────────────┤
│ 左栏 菜单  │ 主区（随状态切换）             │ 右栏 伴随层 │
│           │                               │ (B/Copilot)│
│ 数据蓝图   │ ① 数据蓝图（ER 可视化）       │ 建议卡片   │
│ 界面       │ ② 界面清单（已生成页面）       │ 仅需要时   │
│ 流程       │ ③ 流程编排（业务流程步骤）     │ 出现       │
│ ────────  │ ④ 工作台运行时（真实系统）     │            │
│ 访客留言页 │                               │            │
│ 后台管理页 │                               │            │
├───────────┴───────────────────────────────┴────────────┤
│ 命令层 (A/Command)  "加一个留言状态字段…"      [发送]    │
└────────────────────────────────────────────────────────┘
```

- 左栏收纳的是**这一套部署内部**的构建对象（蓝图/界面/流程）与已生成的业务菜单，不再横向罗列多套系统；切换系统走左上角"返回部署清单"。
- 进入展厅/运行态后，构建类菜单与命令层隐藏，只剩业务菜单（按角色裁剪，见 4.6）。

### 4.3 主区的四种状态（对应旅程三阶段 + 运行）
| 状态 | 内容 | 何时进入 |
|---|---|---|
| 蓝图 | ER 可视化 + 提案卡流 | 建表、改结构 |
| 界面 | 已生成页面的清单与预览 | 生成界面、组装菜单 |
| 流程 | 业务步骤编排 | 编排流程 |
| 运行 | 工作台真实界面 | 使用、演示、问答 |

**过渡动画**：状态切换时以小砖块拼接/拆解的过渡隐喻"砌墙"（见 6.1），让"这是一个构建中的系统"成为体感。

### 4.4 部署清单首页与部署卡
- 首页不是"项目管理器"，是"**我部署过的系统们**"，主按钮唯一：`[+ 部署一套系统]`。
- **一套 = 一张卡**：业务化名称、验证的是什么、状态、数据量、入口、动作。

```
┌──────────────────────────────────────────────┐
│ 留言板 · 验证「访客反馈收集」                    │
│ ● 运行中 · 2 小时前部署 · 12 条数据             │
│ 入口：http://192.168.x.x:port/app/guestbook       │
│                                    [打开] [演示] │
│  [分享]                         [停止] [销毁]   │
└──────────────────────────────────────────────┘
```

- **动作按使用频率排**：打开 / 演示高频在前，停止 / 销毁低频在后；销毁给二次确认并提供"先导出数据"。
- **运行中**默认铺开；**已停止 / 历史**默认折叠——"用完即弃"不该堆成越来越长的列表。
- **默认保留**（2026-09-15 决策）：部署不自动清理，只有用户主动停止/销毁；停止保留数据可再启，销毁数据一并清掉。
- **分享**（DR-04，2026-09-15 **定板支持分享**）：每套部署有独立入口，可分享给他人演示/使用；MVP 期入口仅本机/局域网可达，分享链接绑定身份 M3(P2) 实现。
- **访客（DR-04）**：除三层成员角色外，`公开页面`（如访客留言页）允许**匿名访问者**提交内容——访客不是成员角色，看不到任何菜单与数据，只能提交到公开页面。访客公开页面 M3(P2) 交付；**MVP 期的"留言板"场景由成员在后台管理页代录访客留言**，界面话术为"访客留言可由成员代录，公开提交页下阶段开放"。

### 4.5 部署流：一屏三步
```
① 你要验证什么？  「做个留言板收集访客反馈」   数据：●从零建 ○接已有的（下阶段开放）
   ↓
② 系统设计提案（生成即提案，全是业务话）
   · 留言表（访客、内容、时间、状态）   · 界面：访客留言页 + 后台管理页
   [关系缩略图]      ☑ 附带演示数据（默认勾选）
   [就这么部署] [调整一下] [逐张修改] [换个描述]
   ↓
③ 部署中…（秒级，进度可见不表演）
   建库 → 建表 → 回读 → 生成页面 → 演示数据 → 注册入口
   ↓
✔ 就绪：入口 http://192.168.x.x:port/app/guestbook   [打开] [演示]
```
- 数据模式选择就在第一步旁边，是一句人话："数据从零建，还是接已有的？"，不出现"模式"二字。「接已有的」MVP 期置灰并注明下阶段开放（DR-09），避免点进去无路可走。
- 提案中不出现"表结构 / CRUD / 外键"这类词（见 5.2 语言纪律）。
- **演示数据开关默认勾选（DR-08）**：就绪后的界面带着真实样子的数据（每表几行、外键值相互匹配），兑现"数据会说话"（P5）；不要可取消勾选；工作台设置里有"一键清空演示数据"（只清种子行，不动后续真实录入）。
- 进度条是"让你看见它真在干活"，秒级的事情不假装复杂；**就绪 = 立刻给出可点开、可分享的入口**。
- **入口地址显示部署主机的实际地址**（DR-17）：MVP 定位单机/局域网——入口按当前访问地址生成本机可达链接（如 `http://192.168.x.x:port/app/guestbook`）；异地演示由部署者自行内网穿透，产品不承诺公网可达。

### 4.6 一套部署内的成员与权限体验（P1 必做）
- 三层角色：**创建人**（主人 + 建造者，一切权限，独有工程室）/ **管理员**（全套业务功能 + 数据管理动作）/ **操作员**（仅被分配给自己的功能）。
- **管理员边界（DR-14，2026-09-15 统一）**：管理员 = 全套业务功能（所有菜单页面）+ 数据管理（导出、维护、处理异常记录）+ 查看成员与日志；**不含工程室**（不能改模型/改界面/配菜单）、**不含停止/销毁/分享**（创建人独有）；成员增删与授权变更同样是创建人独有，管理员只看得到成员名单。
- 配置交互不做 RBAC 矩阵，做"**把功能分给人**"——在菜单功能树上勾选**分给某个人**（不是分给角色），不出现"权限/角色/数据域"措辞。同为操作员的两个人可以分到不同功能：

```
成员与权限 · 库存管理系统
创建人  老猫（你）
管理员  王姐  —— 查看所有功能
操作员  小李  —— ☑ 入库单 ☑ 库存查询
操作员  小张  —— ☑ 质检单 ☑ 退货处理
                         [+ 添加成员]
```

- **界面按角色裁剪**：操作员登录后只见分给自己的菜单——裁剪既是安全也是清爽（授权按人存储，见技术路线 §七）。
- **数据级先做简单版**：操作员有"我的记录"入口（只见自己录入的），全量数据归创建人/管理员；复杂行级权限以后再说。
- 添加成员：输入对方账号，或生成访问链接、对方进入即绑定身份（M3/P2）。
- **访客不是成员**：匿名访问者走公开页面（见 4.4），不进这个配置界面。

### 4.7 操作日志：每套系统自带的"流水账"（P1，固定能力）

业务快速验证时系统是要给真人真用的，"这条采购单谁改的、那张退货单什么时候没的"必须翻得到。操作日志因此是每套部署的**固定件**——不生成、不配置、不能关，部署一就绪就在；它不在工程室里，而在运行态的业务菜单区，和"我的记录"一样是系统自带的一页。

**入口与可见性**

- 创建人/管理员的运行态菜单里常驻"操作日志"；操作员看不到全局入口，只在自己相关的记录上看到自己的动作。
- 它是给管事的人还原现场用的，措辞上始终叫"操作日志"，不叫"审计/监控"——避免给一线成员"被监视"的压迫感。

**这一页长什么样**

```
操作日志 · 库存管理系统
[ 全部动作 ▾ ] [ 全部的人 ▾ ] [ 全部业务 ▾ ] [ 近 7 天 ▾ ]      [导出]
──────────────────────────────────────────────────────────────
今天 14:32   小李  修改了 采购单 #1042
             单价 38 → 42；数量 50 → 60            [查看这条记录]
今天 11:05   王姐  删除了 退货单 #88（退货原因：破损 2 件）
昨天 17:48   小李  新增了 入库单 #2031
昨天 09:12   老猫  修改了成员：小张 获得「退货处理」
09-10 10:01  系统  部署就绪（创建模式 · 4 张表）
```

- **时间倒序、一条一行**：时间 · 谁 · 做了什么 · 哪条业务记录；点开才看字段级改动，默认不摊开。
- **人话描述**："修改了 采购单 #1042 / 单价 38 → 42"，不出现表名、字段名、SQL；技术标识收进展开层。
- **删除留痕**：记录已不存在，但日志保留可辨认的摘要（单号 + 关键字段），不让链接点进去是死路而摘要也没有。
- **筛选只给四个最常用的**：动作（增/改/删/系统动作）、人、业务对象、时间段。不做复杂检索器。

**两个方向都能走**

- 从日志的一行 → `[查看这条记录]` 跳到记录现状（若还在）。
- 从任意业务记录的详情页 → "操作记录"小标签，看到它被谁改过几次，不必专门跑去日志页。

**三条体验底线**：日志只追加，界面上没有编辑和删除入口；只读浏览/查询不留痕（不做行为监控）；停止不丢、随部署销毁而消失，销毁前随"导出数据"一并导出。（日志一致性在技术上由"两阶段写入 + 启动对账"保证，见技术路线 §五——业务库与元数据库是两个库，不存在跨库事务；对用户呈现不变。）

## 五、关键界面规格

### 5.1 命令层（A 形态）— 最常用的输入口
- **外观**：底部通栏输入框，占位符给出场景提示："试着说：帮我建一个进销存模型，能管采购和库存"。
- **多轮上下文**：命令层记住本次"砌墙"的对话（右上角一个小的时间线图标可展开历史）。
- **智能建议**：输入时联想"我有一张 Excel 表，帮我导进来""给客户表加个地区筛选"等高频动作。
- **提交后**：命令转化为一张提案卡，落到当前主区，命令栏自动清空待命。

### 5.2 提案卡（原则 P2 的实体化）— 全产品统一的"AI 产出物"
所有 AI 产出用同一张卡呈现，字段统一：

```
┌──────────────────────────────────────────────┐
│ 提案 · 进销存数据模型                  [新]     │
│ ────────────────────────────────────────────  │
│ 我根据你的描述建了 4 张表：                     │
│  · 商品表 —— 记录在售商品与成本                  │
│  · 供应商表 —— 记录供货方信息                   │
│  · 采购单 —— 记录每一次进货，对应哪个供应商       │
│  · 采购明细 —— 一张单里每一行买了哪件货、几件     │
│  ┌─────────────┐  [查看关系图]                 │
│  │  ER 缩略图  │                              │
│  └─────────────┘                              │
│ [就这么部署] [调整一下] [逐张修改] [换个描述]    │
└──────────────────────────────────────────────┘
```
- **语言纪律**：说明文字只讲业务含义，不讲技术术语（"外键"写成"关联 supplier_id"这种也不行——直接说"每次进货对应哪个供应商"）。技术措辞全部收进展开层。
- 主操作是 **「就这么部署」**——确认后才真正建库建表、秒级就绪（生成即提案，不确认不落库）。
- 四个操作里，**"逐张修改"**是控制感的关键：点开即进入蓝图的单表编辑。

### 5.3 数据蓝图（阶段②的核心）— 业务人看得懂的关系图
- **默认视图**：业务化 ER 图。表名显示中文业务名（"采购明细"），关系线上用**动词标注**（"包含""属于""记录自"），而非 FK 符号。
- **字段交互**：默认只显示关键字段（名称、类型以中文呈现，如"数量 · 数字"）；点表节点展开全部字段。
- **空状态引导**：首次进入时有一句话引导——"先告诉我你的业务，我来搭第一块砖"，光标停在命令层。
- **增量修改**：用户在图上直接说（命令层）或点（直接操作）均可：加字段、改关系、合并表。

### 5.4 界面清单与菜单组装（P1/P2）
- 每个生成的界面是一张**可运行缩略卡**：缩略图直接渲染真实界面（带演示数据），不渲染设计器。
- **"生成即真"原则**：默认进入"运行预览"，微调是次级动作（点界面卡上的"调整"才进入编辑，而不是常态处在一个拖拽设计器里）——因为用户要的从来不是"设计器"，是"能跑的样子"。
- 菜单组装 = 把界面卡拖进左侧导航树的对应节点，即拖即存。（对标：手写系统时的"路由配置"，但用拖拽完成。）

### 5.5 工作台运行时 + 演示模式（展厅）
- 工作台就是"最终系统的样子"：左侧业务菜单 + 主内容区，和任何正规业务系统无差别。
- **演示模式**（顶栏一键）：全屏、自动隐藏左栏构建痕迹、隐藏命令层与伴随层、隐藏提案卡与状态标签。只剩：干净菜单 + 运行界面 + 数据。
- 离开演示模式需 `Ctrl/Cmd+Shift+D`，防止演示中误触；提供"演示专用数据"开关（可选：展示脱敏假数据，避免现场暴露真实数据）。

### 5.6 问数据（C 形态）— 工作台上的数据对话
- 入口固定在运行态右上角。
- 回答 = 视图卡片：**一句话结论 + 数据表/图表 + 可展开的"它怎么查的"（SQL/条件）**。
- 图表用自绘 ECharts 规格驱动渲染（已定不联动 superset-lite），视觉与卡片语言保持一致、克制。
- 视图卡片支持"钉到工作台"，变成常驻报表卡片——从"问一次"到"建一个报表"。

### 5.7 流程向导（P2/M3 交付，DR-06）— 把"按步骤办事"砌进系统
业务流程是产品承诺的核心能力之一（见产品一页纸），v0.2.1 起明确其形态与交付时点——**向导式流程，不做工作流引擎**：

- **是什么**：一条业务流程 = 一串**页面步骤**（如 收货登记 → 质检 → 入库确认），每步绑定一个已生成的页面、一个完成条件和一个**状态字段**；操作员按"下一步"依次完成，状态字段随步推进（待质检 → 已质检 → 已入库）。
- **不是什么**：不做复杂审批链、不做条件分支引擎、不做跨系统流转——验证场景的流程是"引导人按顺序办事"，不是 BPM。
- **入口与形态**：工程室左栏"流程"进入编排（主区第③状态）；运行态里流程以**向导页**呈现——顶部一条步骤条（已完成/当前/待做），主区就是当前步骤的页面。
- **语言纪律**：步骤名用业务动词（"收货登记"），不出现"状态机/节点/流转"。
- **交付时点**：M3（P2）。一页纸中"简单业务流程"的承诺随本条从 P1 调整到 P2（见决策记录 DR-06）——P1 先把"页面 + 权限 + 日志"做扎实，流程在这之上叠。

## 六、视觉与动效语言

### 6.1 气质定位
- **克制的生产力工具**，参照 Linear / Notion / Tableau 家族，不参照"科技感霓虹"。
- 理由：这是要**当场演示给客户看**的工具，气质必须让观者觉得"专业、可信、像正经系统"，而不是"炫技的 AI 玩具"。

### 6.2 色彩
- 基调：暖灰 + 白（工程感），主色用**砖色系**（陶土橙 #C15F3C 一带）呼应"瓦匠"，少量交互强调色。
- 数据强调色：蓝（信息）/ 橙（警示）/ 绿（健康），克制使用，服务数据含义而非装饰。
- 深色模式作为可选第二主题，默认浅色（演示场景光线不可控，浅色容错高）。

### 6.3 组件基调
- 卡片（提案卡/界面卡/报表卡）是**第一组件**，圆角适中（8px 级），阴影轻。
- 所有"AI 产出物"共用卡片语言 → 用户在肌肉记忆层面形成"这是 AI 给的、我可以审"的认知。

### 6.4 生命周期状态色
- 对齐部署五态：**草稿**（灰描边）→ **部署中**（主色脉动 + 进度）→ **运行中**（主色实点）→ **已停止**（淡灰，可再启动）→ **已销毁**（不进列表，仅留导出提示后的告别态）。
- **默认保留**：运行中与已停止都保留在清单（已停止默认折叠）；销毁是唯一清数据的动作，二次确认并先给导出机会——弃得干净，才敢建得大胆。

### 6.5 动效纪律
- 状态切换用**砖块拼接**隐喻（300ms 内，克制的位移+透明度）。
- 提案卡出现时不做夸张动画——**它是要审的东西，不是惊喜**。
- 整体原则：动效服务于"理解结构"，不服务于"炫耀生成"。

**MVP 的体验验收点（可用一句话测试）**：
1. 一个没看过产品的人，能不能在 2 分钟内完成"部署 → 描述一个业务 → 看懂提案 → 就这么部署 → 拿到入口"？

3. 接受建表后，用户能不能**不靠 AI**在蓝图里解释"这张表为什么这么建"？（蓝图 UI 在 M2，MVP 期以提案卡的业务说明替代）
4. 全程有没有任何时刻用户感到"我不知道它要干什么"？（黑盒感 = 失败）

## 八、风险与开放问题

| 风险 | 说明 | 设计侧缓解方向 |
|---|---|---|
| 业务化描述 vs 准确性的拉扯 | 把外键翻译成"包含/属于"可能丢失精确性 | 动词标注由 AI 生成+人工可改；技术层永远可展开 |
| 对话历史变长后的迷失 | 多轮生成后,用户忘了系统是怎么长成这样的 | 左栏以结构（表/界面/流程）为准，对话只是过程噪音,不承担导航职责 |
| 生成质量决定信任天花板 | 一次烂提案可能劝退 | 提案卡保持"低承诺"：强调可改可弃,不渲染"完美生成" |
| 演示模式误触真实数据 | 现场暴露敏感数据 | 演示专用脱敏数据开关（5.5） |
| 销毁误操作 | 销毁清数据不可逆 | 默认保留 + 停止/销毁分开 + 二次确认 + 销毁前导出（4.4 / 6.4）；操作日志随导出一并带走 |
| 日志变成"监控感" | 成员知道一举一动都被记，拘束、不敢用 | 只记增删改与关键系统动作、不记浏览；文案统一叫"操作日志"，定位"出问题能还原"而非"盯着谁"（4.7） |
| 日志量与性能 | 真用起来写入频繁，日志页可能变长变慢 | 只追加、分页 + 时间/对象筛选；日志存元数据库、按 deployment_id 隔离索引，不跨系统堆积（一致性由两阶段写入 + 启动对账保证，见《设计细化》§十一 五） |
| 自绘图表表现力上限 | ECharts 轻量封装可能满足不了复杂专业看板 | P3 先覆盖问数据常见图表类型；复杂看板需求以后另议，当前明确不联动 superset-lite |
| 异地演示的网络可达性（DR-17） | 演示分发隐含"客户如何访问"，MVP 无公网能力 | MVP 限单机/局域网，入口显示部署主机实际地址；异地演示由部署者自行内网穿透；产品不承诺公网，P2 评估 |
| 演示数据混淆真实数据 | 就绪即带演示数据，真用时可能忘记清 | 种子行带标记可一键清空（只清种子、不动真实录入）；演示模式可叠加脱敏开关 |
| ~~桌面端 vs 浏览器的形态~~（已定） | 本地库偏桌面、演示分发偏 Web | 决策：只做 Web 版（2026-09-15）；本地 SQLite 由 Web 服务端进程管理，天然支持演示分发，不做 Tauri 桌面壳 |
| ~~图表方案~~（已定） | 自绘 ECharts vs 联动 superset-lite | 决策：自绘 ECharts、规格驱动，不联动 superset-lite（2026-09-15） |

**仍待确认（0 项）**：原「每套部署入口是否支持分享给别人」已于 2026-09-15 **定板支持**（DR-04）——MVP 限本机/局域网可达，分享链接绑定身份与访客公开页面随 M3(P2) 交付。
