## 一、为什么是这件事

### 1.1 现状：起点已有「全自动」与「混合」两条路

当前创建模式（数据从零建）在首页「部署一套系统」下拉中提供两种入口（`dashboard/src/pages/Deployments.tsx` + `dashboard/src/pages/deploy/DeployWizard.tsx`，后端 `src/datamason/deploy/service.py`）：

```
全自动：一句话 → LLM 一次生成完整 SchemaSpec（表+字段+关系+页面）→ 提案卡 → 就这么部署
混合  ：一句话 → LLM 表骨架 → ER 图示确认 → 逐表 NL 引导字段 → 合并 → 同一 confirm 落库
```

两者共同前提是 **LLM 参与造 spec**：前者一次到位，后者分段提案，但都依赖自然语言与模型。

### 1.2 真实缺口：懂结构的人，被关在了「描述」门外

| # | 现象 | 根因 |
|---|---|---|
| 1 | **专业用户心里已有表结构**：DBA、实施、懂业务又懂库的人，脑中/文档里已是「表、字段、主外键、类型」，却要先把它翻译成一句自然语言，再让模型「翻译回」结构——两次转译，偏差与等待都在这里产生 | 现有入口只接受 NL，不接受结构本身 |
| 2 | **没配 LLM 就无法建库**：模型未配置或离线时，创建模式无任何可用入口；而建表本是确定性工作，不该被一个外部服务卡死 | 造 spec 的唯一通道是 LLM |
| 3 | **想直接写 DDL 没有通道**：操作人员习惯用 `CREATE TABLE` 快速落笔，也希望在图形界面上核对关系、补业务名；当前 SQL 与可视化两种形态都不提供给建库环节 | 起点缺少面向专业人员的工作台 |
| 4 | **手写 SQL 与平台元数据如何衔接没有答案**：即使能写 SQL，归属列、单主键、外键指向、页面派生都依赖 SchemaSpec；直接执行用户 DDL 会绕过这套元数据驱动架构 | 缺少「SQL → 中间规格」的确定性桥接 |

### 1.3 0.14.0 的回答：纯手动专业模式（SQL 与可视化，同一份草稿）

> **专业模式**：不调用 LLM，操作人员直接以**两种形态**建表——
> 在 **SQL 编辑器**里写 `CREATE TABLE` 快速落笔，解析为结构提案；
> 在**可视化结构工作台**上增删表/字段、连线外键、补业务名与类型；
> **两种形态操作同一份草稿，随时切换、双向同步**，确认后走既有落库链路。

一句话：**全自动解决「能跑」，混合解决「跑得对」，专业模式解决「我自己来、且更快」**。它延续「生成即提案，确认才落库」，但提案的作者从 LLM 换成了人——零 token、可离线、结果确定。

## 二、版本范围与边界

### 2.1 范围内（M8 单轨）

| 轨 | 能力 | 一句话 | 主要使用角色 |
|---|---|---|---|
| **M8 专业建库** | 创建模式下「SQL 建表 + 可视化建表」双形态、同一草稿、随时互转，确认后复用 confirm 落库 | 懂结构的人直接落笔，不经过 LLM | 创建人 / 平台管理员（工程室） |

### 2.2 明确不做（边界）

- **直连（link）模式不开放专业建库**：直连语义是「接进来、反向反射」，维持 DR-27 只读红线；专业模式与混合模式（DR-39）一致，仅对创建模式（DataMason 自建库）开放。
- **不引入新前端运行时依赖**：SQL 编辑器不引入 Monaco/CodeMirror/xterm，基于 antd `Input.TextArea` 自研受限编辑（等宽字体、语句与错误定位、基础片段），维持前端零新增运行时依赖纪律（DR-36 口径延伸）。
- **不直接执行用户书写的 DDL**：SQL 一律经 sqlglot 解析、归一化为 SchemaSpec，再由 `build_schema_ddl` 按目标方言确定性生成后落库。用户 SQL 是「结构输入」，不是「执行脚本」。
- **草稿不做服务端持久化**：沿用 DR-37——草稿在浏览器内存维护，确认时一次性提交完整 spec；刷新/关闭丢失（界面提示）。不做 draft 表、不做多人协作。
- **类型只收敛到既有八类列**：INTEGER / BIGINT / VARCHAR / TEXT / BOOLEAN / DATETIME / DECIMAL / FILE。无法映射的源类型（如 JSON/BLOB/ENUM/几何/自定义类型）在解析阶段明确报错并提示改用受支持类型，不做猜测式降级。
- **不做存储过程 / 触发器 / 视图 / 索引（除主键外）/ 分区表**：解析到此类 DDL 对象直接拒绝并说明本版不支持；平台页面与 CRUD 由表结构派生，不消费这些对象。
- **FILE 附件类型不从 SQL 字面量产生**：SQL 方言无对应列类型，FILE 列在可视化形态设置；SQL 中以 `VARCHAR` 承载、再到可视化形态标记为 FILE（见 §3.6）。
- 沿用既有边界：表重命名迁移、跨库结构迁移、数据清洗引擎、新测试框架等不做。

## 三、能力设计：专业建库（M8）

### 3.1 入口：与「全自动」「混合」并存，不替换

首页「部署一套系统」下拉在现有两项后增加第三项（`Deployments.tsx` 菜单 items 追加）：

| 菜单项 | 落地 | 适用 |
|---|---|---|
| 全自动（简单业务） | 现状一键流，不动 | 简单/验证型需求 |
| 混合引导（复杂需求） | 现状 HybridBuilder，不动 | 复杂/正式需求 |
| **纯手动 · 专业模式**（新增） | 直达 ManualBuilder（SQL + 可视化） | 懂结构、要离线、求确定 |

`DeployWizard` 的 `initialBuilder` 联合类型由 `"auto" | "hybrid"` 扩为 `"auto" | "hybrid" | "manual"`；`manual` 与现状 hybrid 一样直出独立构建器，不套全自动向导壳。

### 3.2 单工作台、双形态（非多步向导）

与混合模式的四步流程不同，专业模式是**一个工作台、两种形态**，操作人员在同一屏内落笔与核对：

```
                 ┌─────────────── 同一份草稿（SchemaSpec）──────────────┐
                 │                                                      │
   SQL 形态  ──写 CREATE TABLE──► 解析为 spec ──► 写回草稿 ──► 可视化即时同步
   可视化形态 ──增删表/字段/连线──► 直接改 spec ──► 草稿 ──► 一键反生成 SQL
                 │                                                      │
                 └──────────── 校验通过 → 复用 confirm 落库 ─────────────┘
```

- **形态切换**：`Segmented`（SQL / 可视化）切换；宽屏下可左右分栏（SQL 在左、结构预览在右），窄屏退化为切换态。布局只做这一种，不做多套编排。
- **目标位置**：沿用 HybridBuilder 的 `targetConnId`——默认独立 SQLite；选择 MySQL/PG 服务器连接时在其上新库落库。目标方言决定解析口径与最终 DDL 生成。
- **系统名称/用途**：工作台顶部填写（沿用现有字段），不新增概念。

### 3.3 SQL 形态：写 DDL，解析成结构提案

**输入**：一条或多条 `CREATE TABLE` 语句（按目标方言书写：sqlite/mysql/postgresql）。

**解析（新领域模块，纯 Python）**：
- 用 sqlglot 以目标方言 `parse`，仅接受 `exp.Create` 且为建表；其他语句（INSERT/ALTER/索引/视图/触发器/事务/命令）一律拒绝并按语句位置报错。
- 逐表抽取：表名、列名、列数据类型及长度/精度刻度、`NOT NULL`、主键（内联或表级 `PRIMARY KEY`）、`UNIQUE`、`FOREIGN KEY ... REFERENCES` 及目标表/列、自增标记。
- 类型归一到八类列（映射见 §3.6）；不支持类型、无主键、复合主键、重名列、引用目标不存在等，返回**定位到语句/表/列的可读错误清单**，不整体失败。
- 归属列与骨架主键的处理见 §3.5，不要求用户书写。

**输出**：与 skeleton 合并器一致形态的结构提案（表 + ColumnSpec 列表），写回草稿后可视化同步呈现；不直接落库、不直接执行。

**编辑器（自研，零新依赖）**：
- antd `Input.TextArea`，等宽字体（尺寸/颜色取 `--fn-*`，不硬编码）。
- 解析错误在错误列表中按「表/列 + 信息」列出，点击滚动定位到大致行；不做语法高亮自动补全（无 Monaco），提供 `CREATE TABLE` 基础片段与「清空 / 示例」入口。
- 离开/刷新前若有未部署改动，沿用 beforeunload 提示（与 HybridBuilder 一致）。

### 3.4 可视化形态：结构工作台，复用既有画布与字段编辑

复用 0.12.0 已交付的 `ErCanvas`（节点增删/改名、连线增删、字段展开）与字段行编辑交互，作为专业模式的可视化形态：

| 能力 | 复用/新增 |
|---|---|
| 表节点增删、改表名/业务名 | 复用 ErCanvas |
| 连线=外键列、删线=删外键列 | 复用，单一数据源 = 字段定义（DR-38） |
| 字段行编辑（名/业务名/类型/长度/可空/唯一/主键/外键目标） | 复用 FieldEditor 行交互 |
| **FILE 类型标记** | 可视化形态提供（SQL 形态不产生，见 §2.2/§3.6） |
| 整库结构总览 | ErCanvas 只读视角 + 校验状态角标 |

可视化的每一次操作都直接修改同一份 SchemaSpec 草稿；切换到 SQL 形态时由草稿**反生成**目标方言 DDL（经 `build_schema_ddl` 的渲染能力或等价确定性序列化），保证两形态不出现两套真相。

### 3.5 主键与归属列：系统补齐，不进用户视野

- 用户 SQL/可视化只需给出业务列；每表主键沿用平台约定（INTEGER/BIGINT 自增 `id`）。若用户 SQL 显式书写了符合平台规则的单列主键则采用；缺省时由系统补 `id`。复合主键、非平台类型主键拒绝并提示。
- 归属列 `created_by/created_at/updated_by/updated_at` 仍由 `inject_ownership_columns` 在落库前统一注入（DR-05）；草稿与 SQL 形态不展示、不要求手写，用户书写同名列按保留列冲突报错。

### 3.6 类型归一映射（SQL → ColumnSpec）

解析按下表把源方言类型收敛到平台八类（sqlglot 数据类型节点 → ColumnType）；未列出类型归入「不支持」并提示：

| 源类型（多方言，示意） | ColumnType | 备注 |
|---|---|---|
| INT / INTEGER / MEDIUMINT | INTEGER | |
| BIGINT | BIGINT | |
| VARCHAR / CHAR / NVARCHAR（n） | VARCHAR | 取长度，越界（1–4000）报错 |
| TEXT / TINYTEXT / LONGTEXT / CLOB | TEXT | |
| BOOLEAN / BOOL / BIT(1) | BOOLEAN | |
| DATETIME / TIMESTAMP | DATETIME | |
| DECIMAL / NUMERIC（p,s） | DECIMAL | 取精度刻度 |
| （可视化标记） | FILE | SQL 不直接产生；如需附件列，SQL 写 VARCHAR，可视化改 FILE |

JSON / BLOB / ENUM / SET / 几何 / 数组 / 自定义类型 → 解析报错并提示改用受支持类型，不做隐式降级。

### 3.7 校验与落库：复用，不新造落库链路

- **校验**：草稿在两种形态下都可随时「校验」——实际为 `SchemaSpec` 强校验（单主键、无重名列、外键存在且指向主键、保留列不冲突）+ 类型归一校验；错误以表/列定位呈现，就地修正。
- **落库**：校验通过后，`spec_json` 直接走既有 `POST /deployments/confirm`。建库（SQLite 独立文件 / MySQL·PG 服务器上新库）、建表、回读、页面派生（`_derive_pages`）、菜单注册、可选种子、入口注册全部沿用。专业模式**只改「造 spec 的过程」，不改「落库的过程」**。
- **可选种子**：专业模式默认不勾选演示种子（结构是人工精确设计），沿用 confirm 的种子开关，由操作人员决定。

## 六、验收标准

**离线（pytest，每任务验收线）**
- 解析：三方言 `CREATE TABLE`（含内联/表级主键、外键、NOT NULL、长度精度）正确归一；不支持类型、复合主键、重名列、自环、悬空外键、非建表/多语句混杂分别拒绝并给出表/列定位；
- 归一后结构通过 `SchemaSpec` 全校验（单主键/外键存在且指主键/保留列不冲突）；归属列不要求手写且由系统注入；
- 接口：解析接口不执行、不落库、不调 LLM、不写 ai_generations；link 模式返回拒绝；
- 落库：专业模式确认 == 既有 confirm 链路，全自动/混合无回归。

**真实浏览器（Playwright，里程碑验收线）**
- 首页下拉出现第三项，三种模式并存，旧两项行为不变；
- 写「客户/订单/商品」多表含外键 SQL → 解析后可视化即时呈现表与连线；
- 切到可视化改一列类型、把一列标记为 FILE、删/加一条连线 → 切回 SQL 文本对应变化；
- 故意写一个不支持类型（如 JSON）与悬空外键 → 错误定位到表/列，修正后通过；
- 在**未配置任何 LLM** 的情况下成功部署 → 工作台菜单出现、可录数据；
- 直连模式不出现专业模式入口（红线）。

**版本级**：独立验收报告（`docs/验收/2026xxxx-0.14.0-项目验收报告.md`），M8 验收线全绿。

## 八、风险与开放问题

| 风险 / 开放问题 | 说明 | 缓解 / 决策点 |
|---|---|---|
| **R1 方言解析差异** | 三方言 DDL 语法、类型、自增写法差异大，sqlglot 个别边角语法可能解析偏差 | 以目标方言口径解析；M8-0 用三方言真实 DDL 样本做表驱动测试；解析不明确宁可报错提示改写，不猜测 |
| **R2 双向同步复杂度** | SQL 文本是自由文本，可视化改动反生成 SQL 可能覆盖用户手写格式/注释 | 明确口径：SQL 形态承载结构语义，不保留手写注释与排版；切形态前提示「将按结构重排」；草稿以 SchemaSpec 为准（DR-44） |
| **R3 编辑器体验落差** | 无语法高亮/补全，专业用户可能觉得简陋 | v0 收敛为「能写、能定位错误、有片段」；若高频反馈再立 DR 评估编辑器依赖，不提前引入（DR-43） |
| **R4 类型表达力受限** | 用户依赖 JSON/ENUM/BLOB 等类型，八类无法表达 | 解析阶段明确提示替代方案（VARCHAR/TEXT）；记录反馈高频项，作为后续版本扩展类型的依据，本版不隐式降级 |
| **R5 草稿中断丢失** | 单工作台中途刷新/关闭草稿丢失 | 沿用 DR-37，界面提示「草稿在本地、关闭即失」；不提前做服务端持久化 |
| **Q1（待确认）** | 宽屏默认左右分栏还是默认单形态切换 | 规划倾向宽屏分栏（左 SQL、右结构）、窄屏切换；技术方案阶段按现有响应式断点定稿，不新增布局开关 |
| **Q2（待确认）** | 专业模式默认是否勾选演示种子 | 规划倾向**默认不勾选**（人工精确结构）；沿用 confirm 种子开关，操作人员可自行开启 |
