# DataMason 0.11.0 版本规划 — 让系统「长得大 · 用得全 · 分得清」

> **基线**：0.10.0（Gitea tag `0.10.0`，里程碑 M0–M4 已全部验收）。本文件在其之上规划下一个次版本 **0.11.0**（里程碑 **M5**）。
> **依据**：《产品一页纸 v0.2》§九「决策裁决归档 DR-01~25」、《设计细化 v0.2.1》§十一「技术实现参考」、《体验设计细化 v0.2.1》。
> **配套**：《DataMason-0.11.0-技术方案与实现闭环.md》（同目录）——元数据变更、接口契约、UX 落库动作、迁移兼容与测试点。
> **维护规则**：本文件出现的新跨文档概念，先按《产品一页纸》§九·四 追加 DR 条目（本文件 §八 已给出拟追加清单 **DR-26~DR-33**），再改对应章节。0.10.0 三份基线文档保持冻结快照不动。

---

## 一、为什么是这三件事

0.10.0 已经跑通「一句话建库 → 建表 → CRUD 界面 → 菜单 → 流程向导 → 问数据」的完整链路，并且带上了成员、日志、分享、API 开放、配置包导出。把 0.10.0 当"一版能演示、能真用的系统"来看，真实的咨询/内部信息化场景会立刻撞到三堵墙：

| # | 真实缺口 | 用户的原话 | 0.10.0 的现状 |
|---|---|---|---|
| 1 | **系统建完就"冻住"** | "业务又多了一张台账，旧的那张不用了——我只能重建一套系统吗？" | 结构编辑只到**字段级**（增删/改名/改类型，且受主键/归属/外键保护）；**没有增表、删表**。`table_specs` 只在部署 `confirm` 时写入一次。 |
| 2 | **表单只能录字段** | "报销单要传发票、合同要附扫描件；存量数据几百行能不能 Excel 导进来？导出去能不能直接给同事？" | **零文件能力**（无上传/无附件/无预览）；导出只有 CSV（≤5000 行）；**无导入**（DR-16 曾列为 P2+ 备选、未绑里程碑）。 |
| 3 | **分工表达不了** | "这批人只要能看不能删；那批人不能看金额；每个人的数据范围也不一样。" | 权限只有两层：①「这个功能分给谁」（菜单级，`deployment_menu_grants`）②「操作员只看自己录的」（硬编码 `created_by = 自己`）。**没有按动作授权、没有数据范围配置、没有字段级控制**。 |

这三件事不是三个孤立功能，而是同一件事的三个面：**让一套已经跑起来的系统，能继续长（结构）、能正式用（文件/批量）、能放心交给别人（权限）**。因此 0.11.0 的主题定为：

> **可长（结构演化）· 可操作（附件 / 文件查看 / 导入导出）· 可分管（操作权限 / 数据权限）**

**版本气质**：沿用 0.10.0 的"克制生产力工具"定位——能力是"正经业务系统该有的"，不是"炫技的"。凡是会破坏「数据资产是用户自己的、生成即提案、外部库决不擅动」三条底线的，宁可不做（见 §二·不做）。

## 二、版本范围与边界

### 2.1 范围内（M5 三轨）

| 轨 | 能力 | 一句话 | 主要使用角色 |
|---|---|---|---|
| **M5-A 结构演化** | 对**已部署系统**增表 / 删表 | 系统能长出新表、淘汰旧表；删表前先给"影响面提案卡" | 创建人（工程室） |
| **M5-B 表单操作** | 附件、文件查看、导入、导出增强 | 表单能带附件、能看文件、能批量进出 | 创建人/管理员/（被授权的）操作员 |
| **M5-C 权限细分** | 操作权限（功能×动作）+ 数据权限（行级范围，字段级可选） | "看得见但只能看""能导不能改"这类分工可配置 | 创建人配置，全体生效 |

### 2.2 明确不做（边界，防止无声膨胀）

- **直连（link）模式的任何 DDL**：外部库蓝图仍**只读**，`editor._assert_editable` 红线（`src/datamason/deploy/editor.py:111-117`）保持。增删表只对**创建模式（DataMason 自建库）**开放。理由与替代路径见 §三·3.3。
- **BLOB/大字段落库**：附件一律走"文件存储 + 元数据表"，绝不在业务表里存二进制；不为追求"单文件"而引入 BLOB 列。
- **Office 文档在线预览**：不引入任何在线预览服务/转换器（与"零运行时依赖、可离线"冲突）；docx/xlsx/pptx 给下载，图片/PDF/文本给内嵌预览。
- **复杂行级权限**：不引入组织树、部门维度、权限表达式引擎；数据范围 v0 只做「全部 / 仅自己」两档（字段级只读/隐藏为可选增强，见 §五·5.3）。
- **表重命名、跨表结构迁移、数据清洗规则引擎**：表级增删之外的结构操作不在本版；导入只做基础校验（必填/类型/长度/唯一/外键），不做清洗 DSL。
- **工作流引擎、多表联动事务表单、计算列**：沿用《设计细化》§十一·五 边界不动。
- **断点续传、文件版本、病毒扫描、附件在线协同**：文件能力 v0 只覆盖"传/存/看/删"。

### 2.3 里程碑编号的扩展（需 DR 裁决）

《产品一页纸》§九·四 的维护规则写死「里程碑只允许 M0–M4」。0.11.0 必须扩展编号体系，故拟追加 **DR-26**：里程碑编号向后扩展为 **M5（0.11.0）**，并预留 M6/M7 供 0.12+ 使用；每个版本 = 一个主里程碑（可按轨拆 M5-A/B/C 子轨，子轨不是里程碑号）。**产品 P 编号**（P0–P3 对应 M1–M4）同步扩展为 **P4 = M5**。

## 三、能力一 · M5-A 结构演化：对已有系统增删表

### 3.1 场景与原则

真实系统会生长：业务扩了要加"客户回访表"；方案变了要下线"临时统计表"。0.11.0 让创建人在**工程室的「数据蓝图」页**直接完成增表与删表，全程沿用「**生成即提案，确认才落库**」：

- **增表**：有两种入口，结果都是先出一张**表级提案卡**（结构 + 关系 + 将生成的页面/菜单），确认后才建表。
  - **表单式**：手动填表名/业务名/字段（复用现有 `FieldEditor` 的字段编辑交互）。
  - **一句话式**：输入业务描述，走 0.10.0 已有的 NL→`table_spec` 链路生成单表规格（LLM 仍只产中间规格，Python 确定性映射 DDL）。
- **删表**：先算**影响面**（被哪些表外键引用、涉及哪些页面/菜单/授权/流程/演示数据、预计删除行数），以提案卡呈现；确认后执行。**不提供"一键批量删表"**，每次一张。

### 3.2 增表的关键约束

1. **归属列强制注入**（DR-05）：新表沿用 `inject_ownership_columns`，`created_by/created_at/updated_by/updated_at` 四列必带——否则「我的记录」「操作日志」对新表失效。
2. **外键只能指向已存在表的真实主键**：复刻 `table_spec.py` 的 `_validate_structure` 规则（`SchemaSpec` 层已强制"外键引用目标必须存在、且必须指向主键"），运行时按**该部署已落库的 `table_specs` + 真实 schema**校验，不允许悬空引用。
3. **命名唯一**：`table_specs` 当前**没有** `(deployment_id, name)` 唯一约束，服务层必须显式查重（同时防与真实库同名）。
4. **建表后自动补齐"可被使用"的资产**：新建 `page_specs(kind=crud_list)` + `deployment_menus(kind=table)` + `crud_configs`，与首次部署的产物完全一致；新菜单**默认不授权给操作员**（沿用 M2-5/M3-2 约束，界面标"需授权"）。
5. **建表即写日志**：`activity_logs` 记 `action=structure, object_kind=table`，可读摘要（"新增表：客户回访）";两阶段写入沿用 DR-03。
6. **停止态允许**：结构演化是工程动作，已停止（数据保留）的部署同样可增删表；销毁态不可。

### 3.3 两种数据模式的边界（关键裁决，拟 DR-27）

「对已存在的数据库添加、删除表」有歧义，必须显式裁决：

| 解读 | 含义 | 本版裁决建议 |
|---|---|---|
| **A. 已部署的自建库** | DataMason 创建模式下建出来的物理库，运行一段时间后要加/减表 | **开放**（M5-A 核心）。DataMason 拥有该库，`_assert_editable` 已放行创建模式。 |
| **B. 已连接的外部库** | 直连模式下挂在别人的 MySQL/PG/SQLite 上，要对**外部库**做 DDL | **维持红线，不开放**。0.10.0 已多次裁决"绝不 ALTER 外部库"（DR-05、M2-7/M2-8 守卫、`editor._assert_editable`）；擅自改外部库会破坏"数据资产是用户自己的、我们只搭操作层"的产品承诺。 |

**对外部库的替代路径（本版不做，列入 §九 待确认）**：若确有"外部库也要改结构"的强诉求，0.11.0 之后另立 DR，走**显式危险区 + 影响面提案 + 二次确认 + 绝不隐式执行**的形态单独评估；本版坚持"外部库只读纳管"。**请老猫在开工前确认此裁决**（§九·待确认 Q1）。

### 3.4 删表的影响面与守卫（拟 DR-31）

删表是本版**风险最高**的动作，默认从保守：

**前置影响面提案卡**（不执行、只计算）必须列出：
- 该表行数；演示种子数据登记行数（`deployment_seed_rows`）；
- **被哪些表的外键引用**（含引用列与行数）——SQLite/MySQL/PG 均查；
- 关联的页面（`page_specs.table_id`）、菜单（`deployment_menus.ref_id → page_specs.id`）、以及这些菜单上的**授权**（`deployment_menu_grants`）；
- 关联的流程步骤（`flow_specs.steps[].page_id`）与钉住报表（dashboard 依赖该表则一并提示）；
- 该表的**操作日志停留在原地**（日志属于系统、按 DR-03 只追加，不因删表而回删；导出时随包带走）。

**守卫规则（v0 保守）**：
1. **被其他表外键引用的表，禁止删除**——沿用 `migration.py._protected_reason` 的既有哲学（"FK 列/被引用列受保护"）。提示用户先处理引用方（本版不提供"级联删引用方"）。这条同时绕开了跨库/方言下"先删约束再删表"的复杂度。
2. **被流程步骤引用的表，禁止删除**——先移除相关步骤/流程；避免流程指向不存在的页面。
3. **必须二次确认**（输入表名或勾选确认），并在确认前提示「建议先导出配置包/数据」（复用 0.10.0 已有的导出入口）。
4. **删除是物理且级联的**：`DROP TABLE` + 清理该表的 `PageSpec`（连带其挂载菜单、菜单授权、dashboard 引用）、`CrudConfig`、`deployment_seed_rows`、以及指向它的外键下拉缓存（无缓存则无）。级联顺序沿用 `destroy_deployment` 的"先子后父"手法（`src/datamason/deploy/service.py:643-668`）。
5. **日志留痕**：`action=structure`，可读摘要含"删除表 X（N 行、M 个页面）"。

### 3.5 与现有资产的关系

- `ErGraph` / 蓝图页刷新即可反映新表与新关系；提案卡沿用现有 `StructureProposal` 的卡片语言（`dashboard/src/pages/deploy/BlueprintPage.tsx`、`FieldEditor.tsx`）。
- 运行时白名单来自 `table_specs`（`src/datamason/crud/runtime.py:38-44`），**新增 `table_specs` 行即自动暴露物理表**；删除行即隐藏——但**必须**同时处理页面/菜单/授权，否则会留下"空菜单指向不存在表"的悬垂。
- 操作员的表范围 `member_service.allowed_table_names`（`src/datamason/members/service.py:104-135`）走"菜单→页面→表"，新表默认不可见即由此保证。

## 四、能力二 · M5-B 表单操作：附件 / 文件查看 / 导入 / 导出

### 4.1 附件字段（拟 DR-28）

**形态**：`table_spec` 类型白名单新增逻辑类型 **`FILE`**（"附件"），DDL 侧确定性映射为 `VARCHAR/TEXT`（**存附件 token，不存二进制**），真正的文件落"每部署独立文件目录"，附件元数据落元数据表 `attachments`。这样既让 LLM/表单/列表都按类型识别，又不把大对象塞进业务库。

- **单文件 vs 多附件**：列存 token（单文件）或 token 数组（多附件，JSON 串）。UI 上传按列配置渲染；v0 默认单文件、可选多文件。
- **存储隔离**：`DATA_ROOT/deployments/<部署库文件名去后缀>.files/<随机 token>.<ext>`，与部署的 `.db` 同源同级——天然做到"一套部署一个文件域"。删库/销毁时按 `DATA_ROOT` 守卫整目录清理（复用 `destroy_deployment` 的路径守卫手法 `src/datamason/deploy/service.py:619,627-634`）。
- **安全**：随机 token 命名（不暴露原始文件名/路径）、扩展名与 MIME 白名单、单文件与单请求大小上限（当前全站未设 `MAX_CONTENT_LENGTH`，需在本版显式配置）、`Content-Disposition` 默认 `attachment`（可内嵌预览的仅限图片/PDF/文本）、路径穿越防护。
- **权限**：上传/下载/删除都走成员鉴权；操作员的下载仍受**数据范围**约束（不能下载别人的附件）；**API key 通道默认不开放文件接口**（API key 前缀白名单只放行 `/tables/` 与 `/meta`，文件接口天然不在内，保持默认安全）。
- **日志**：附件的增删随所属行的"新增/修改"以字段级变化留痕（`changes` 里体现附件字段由 A→B）；附件本身不单设监控型日志。**游离附件的清理**：行删除/字段清空时，对应附件标记待回收，由启动对账/懒清理任务回收（不阻塞主流程）。

### 4.2 文件查看

在列表与表单里统一渲染为**文件卡片（FileChip）**，按类型给不同查看方式：

| 类型 | 查看方式 |
|---|---|
| 图片（png/jpg/gif/webp…） | 缩略图 + 点击放大（antd Image 预览） |
| PDF | 内嵌/新标签预览 |
| 文本（txt/csv/json/log…） | 内嵌文本预览（截断大文件） |
| 其他（docx/xlsx/pptx/zip…） | 仅下载（不做在线转换，见 §二 边界） |

### 4.3 导入（拟 DR-29）

**目标**：把存量 CSV/Excel 数据导进任意已生成的表，且**永不盲写**。依赖新增 `openpyxl`（纯 Python、轻量，用于 .xlsx 读写；CSV 用标准库）。

**四步向导（生成即提案的又一次落地）**：
1. **上传**：选择 CSV/XLSX；服务端解析表头与前若干行，落到临时文件（token 引用，定期清理）。
2. **列映射**：自动按**字段名/业务名**匹配（匹配不上给 LLM 建议为可选项，失败回退人工），人工可改；可下载/上传**导入模板**（按表头生成，含示例行）。
3. **校验预览**：逐行做基础校验——必填、类型可转换、长度、唯一（含**文件内重复**与**与库内现有值重复**）、外键存在性（走 `refs` 逻辑）；返回"可导入 N 行 / 错误 M 行 + 错误清单（行号+原因）"，错误清单可下载。
4. **确认导入**：事务策略 v0 = **全量事务**（任一错误则整体回滚，先给错误清单修好再导）；提供"跳过错误行、只导正确行"作为显式选项。导入完成后给出计数报告。

**日志策略（关键，避免日志爆炸）**：批量导入**不逐行写 `activity_logs`**，而是记 **1 条聚合系统动作** `action=import`（`object_kind=table`，摘要含"从 report.xlsx 导入 N 行，跳过 M 行"）。此点需 DR 裁决（§八 DR-29），因为 0.10.0 的语义是"业务写必落日志"，批量导出的逐行日志会淹没日志页。**明细可选**：如确需逐行，另设开关（默认关）。

**权限**：导入/导出是独立动作，受 §五 的"操作权限"控制（例如"只能看不能导"）。

### 4.4 导出增强

- 在既有 CSV（`GET .../rows.csv`，服务端已带当前筛选/搜索/排序）基础上增加 **XLSX 导出**；支持**选择导出列**；把 5000 行硬上限改为可配置上限 + 明确提示（超大导出走分批/流式，或明确告知"已导出前 N 行"）。
- 导出同样受"操作权限"控制；操作员导出的行范围与列表一致（数据范围生效）。
- 说明：**配置包导出**（`GET /deployments/{id}/export`，元数据+日志）与**业务数据导出**是两回事，本版不把附件二进制纳入配置包（可选后续做"配置包 + 附件 ZIP"，本版不做）。

## 五、能力三 · M5-C 权限细分：操作权限与数据权限

### 5.1 现状与目标

0.10.0 的权限是「**菜单级功能授权**」+「操作员硬编码只看自己」：
- 存储只有 `deployment_menu_grants(menu_id, user_id)`；`crud_configs.api_config_json/ui_config_json` 字段存在但**始终为 `{}`、运行时从不读取**（纯占位）。
- 运行时 CRUD 引擎只有两个权限旋钮：`current_user_id` 与 `owner_only`（`src/datamason/crud/engine.py:45-62`、`_owner_condition:204-211`）。
- 前端列表页的"新增/编辑/删除"按钮**完全不看角色**，只要能看到表就能操作（`dashboard/src/pages/workspace/CrudListPage.tsx:133-162`）。

**目标**：把"能做什么"从角色档位里**拆出来**，做成可配置的两维：
- **操作权限**：同一个功能，不同人可做不同动作（查看 / 新增 / 修改 / 删除 / 导出 / 导入）。
- **数据权限**：同一个功能，不同人看到的数据范围不同（全部 / 仅自己），进一步可选**字段级**只读/隐藏。

### 5.2 操作权限（功能 × 动作）

- **交互语言**：沿用「把功能分给人」，**不做 RBAC 矩阵**（体验纪律）。在成员配置里，每个勾选的功能后面跟一排**动作开关**（可看/可增/可改/可删/可导出/可导入），默认值 = 当前行为（不破坏存量）。
- **存储**：扩展 `deployment_menu_grants`，新增 `actions_json`（惰性 `ADD COLUMN` 回填，沿用 M3-2 的 `_backfill_missing_columns` 手法）。空值表示"按角色默认"。
- **强制点**：**服务端统一强制**，不依赖前端隐藏。落点是工作台 CRUD 路由（`src/datamason/workspace/routes.py:217-323`）与 `CrudRegistry`——为 registry 增加 `allowed_actions`，各 handler（create/update/delete/export/import）先校验再执行；create/update/delete 已过 DR-03 日志钩子，权限校验放在钩子之前。前端仅做"按权限隐藏/置灰按钮"，**不作为安全边界**。
- **角色默认**：创建人 = 全部动作；管理员 = 全部业务动作（沿用 DR-14，不含工程/停止/销毁/分享）；操作员 = 显式配置（默认给存量操作员回填当前实际能力，避免升级即失效）。

### 5.3 数据权限

- **行级范围（v0，必做）**：每个功能可配 `data_scope ∈ {全部, 仅自己}`；默认：创建人/管理员=全部，操作员=仅自己（保留 0.10.0 语义）。强制点复用 `_owner_condition`（`created_by = 当前用户`），把"硬编码 true"改为"按配置决定是否施加"。
  - **同一用户对同一表有多个功能时的解析规则**：取最宽（任一功能为"全部"则全部），并在实现闭环中写明——避免"同一表两页范围不一"的歧义。
  - **无归属列的表**：维持降级明示（绝不 ALTER 外部库；创建模式的表都有归属列，故不会触发）。
- **字段级（v0.1 可选，拟不阻塞主计划）**：对指定角色/人配置字段的**隐藏**或**只读**（如"金额字段操作员只读"）。这正好可以**启用一直闲置的 `crud_configs.ui_config_json`**——从"死字段"变成字段级策略的落点。字段级属于"有可能的话实现"的部分，列为 M5-C4，可在行级/操作权限稳定后增量交付；若时间不足，顺延 0.12.0（在 §八 DR-30 写明取舍）。

### 5.4 与既有能力的关系

- **操作日志**：权限变更（授权/动作/数据范围）本身是 `action=member` 的系统动作，继续留痕。
- **API 开放（API key）**：API key 通道是**服务身份**（`registry_for_service`，全表、无归属过滤，`src/datamason/crud/runtime.py:56-73`）。明确：API key **不受**操作权限与数据权限约束（它是系统对系统的通道），但所有 key 动作已标记 `actor_label`；此点写进文档避免误解。
- **流程向导**：`flow/service.py` 的推进逻辑自带 `_scope_cond`（操作员仅自己）——若某功能的数据范围被改为"全部"，流程步骤的范围应随之一致（实现闭环里统一到一个"数据范围解析器"）。
- **公开表单（访客）**：访客提交走系统身份写路径，不受成员操作权限影响；字段级"隐藏"对公开表单的含义（不渲染该字段）需在实现闭环中定义。

## 七、验收标准

**离线（pytest，每任务验收线）**
- 权限：动作越权 403、数据范围过滤、默认回填兼容、API key 服务身份不受限、字段级（若做）隐藏/只读强制；
- 结构：增表（悬空 FK/重名/link 模式/非创建人 各拒绝、语句一致）、删表（被引用/被流程引用禁删、级联无悬垂、外部库快照零变化）；
- 文件：跨部署隔离、路径穿越拦截、大小/类型拒绝、销毁级联清目录、游离回收；
- 导入导出：校验分支、事务回滚、错误清单、聚合日志、xlsx 解析。

**真实浏览器（Playwright，里程碑验收线）**
- **M5-A**：创建人加一张表 → 工作台菜单即时出现 → 录入数据；删一张表 → 影响面卡 → 确认 → 菜单/页面消失、全量 pytest 仍绿；
- **M5-B**：表单上传图片/PDF → 列表可见 → 预览/下载；Excel 导入 20 行成功、含错文件给错误清单；XLSX 导出可用；操作员无导出权时按钮不可见且直调 403；
- **M5-C**：给操作员配"可看可增不可删不可导"+"仅自己"→ 换其登录验证按钮、数据范围与直调 API 均一致；日志页可见授权变更。

**版本级**：独立验收报告（`docs/验收/`，沿用 20260916 的格式），M5 验收线全绿。

## 八、拟追加决策（DR-26 ~ DR-33）

> 按《产品一页纸》§九·四 维护规则，以下先在本规划定稿，开工前**回写**到《产品一页纸》§九 成为正式裁决，再改对应章节。

| DR | 走查问题 | 裁决（一句话） | 主要落点 |
|---|---|---|---|
| **DR-26** | 里程碑编号只允许 M0–M4，无法表达新版本 | 编号向后扩展：**M5 = 0.11.0**，产品侧 **P4 = M5**；预留 M6/M7；子轨（M5-A/B/C）不是里程碑号 | 产品一页纸 §七/§九；设计细化 §十一·十 |
| **DR-27** | 「对已有数据库增删表」是否包括直连的外部库 | **只对创建模式自建库开放**；直连（link）模式维持"绝不 ALTER 外部库"红线；外部库结构变更作为后续独立 DR 议题（危险区形态） | 设计细化 §十一·四/六；本规划 §三·3.3 |
| **DR-28** | 附件怎么存（BLOB 落库 vs 文件+元数据） | **文件存储 + `attachments` 元数据表**；业务表新增逻辑类型 `FILE`（映射 VARCHAR/TEXT 存 token），**不落 BLOB**；每部署独立文件目录；销毁级联清理 | 设计细化 §八；本规划 §四·4.1 |
| **DR-29** | 批量导入的日志语义与 0.10.0「业务写必落日志」冲突 | 导入**聚合为 1 条** `action=import` 系统动作（摘要含文件/成功/跳过行数），**默认不逐行写**；逐行明细为默认关闭的开关 | 设计细化 §十一·五；本规划 §四·4.3 |
| **DR-30** | 操作权限与数据权限存哪、字段级做不做 | 操作权限存 `deployment_menu_grants.actions_json`、数据范围存 `data_scope ∈ {all, own}`（惰性回填，默认兼容存量）；**字段级（隐藏/只读）为可选增强**，启用闲置的 `crud_configs.ui_config_json`，可顺延 0.12.0 | 设计细化 §七/§八；本规划 §五 |
| **DR-31** | 删表的风险控制无定义 | 删表前出**影响面提案卡**；**被外键引用或被流程步骤引用的表禁止删除**（保守，沿用列迁移保护哲学）；二次确认 + 建议先导出；物理 DROP + 级联清页面/菜单/授权/种子/配置 | 设计细化 §十一·四；本规划 §三·3.4 |
| **DR-32** | Excel/CSV 导入（原 DR-16 的 P2+ 备选）何时做 | 需求信号已出现（本轮明确要求），**纳入 0.11.0 M5-B**；新增依赖 `openpyxl`；导入为"预览+校验+确认"提案式，永不盲写 | 设计细化 §十一·三（DR-16 条目追加去向）；本规划 §四·4.3 |
| **DR-33** | 文件/附件能力的安全边界未定 | 随机 token 命名 + 扩展名/MIME 白名单 + 大小上限（显式设 `MAX_CONTENT_LENGTH`）+ 路径穿越防护；**API key 通道默认不开放文件接口**；不引入在线预览/转换服务 | 设计细化 §十一·二/六；本规划 §四 |

> DR-16 的"Excel 导入 P2+ 备选、不绑里程碑"由 **DR-32** 正式改判为"0.11.0 交付"——按维护规则"能力增删必须留痕"，这里写明原因（真实需求出现）与去向。

## 九、风险与开放问题

| 风险 / 开放问题 | 说明 | 缓解 / 决策点 |
|---|---|---|
| **R1 删表是破坏性动作** | 误删业务数据与关联页面 | 影响面提案卡 + 被引用禁删 + 二次确认 + 建议先导出；不批量删 |
| **R2 多方言 DROP/级联差异** | SQLite 外键受连接开关影响；MySQL/PG 约束与依赖顺序 | 被引用表直接禁删（绕开）；级联只清元数据；真库（MySQL/PG）冒烟各覆盖一次 |
| **R3 权限回填兼容** | 存量操作员升级后若不回填会"突然什么都不能做" | `actions_json` 空值=按角色默认（=当前行为）；补一次显式回填与测试 |
| **R4 批量导入的性能/超时** | 大文件同步导入可能超（Flask 单请求） | v0 设行数/大小上限 + 明确报错；超限走后续后台任务（不在本版） |
| **R5 附件占用磁盘无上限** | 文件累积 | 单文件/单请求大小上限 + 部署级容量提示 + 随销毁清理；容量配额列为后续 |
| **R6 权限与 API key 语义混淆** | 有人以为 key 也受权限限制 | 文档显式声明 API key = 服务身份，不受操作/数据权限约束（§五·5.4） |
| **R7 字段级权限复杂度** | 隐藏/只读涉及读写两侧与公开表单 | 列为可选（M5-C4），不阻塞主计划；先定清"隐藏=读不返回、只读=写被拒、公开表单不渲染"三原则 |
| **R8 与 flow/dashboard 的范围一致性** | 数据范围改了，流程/报表是否同步 | 抽出统一"数据范围解析器"，flow/qa/dashboard 复用；列为 M5-C1 的实现要点 |
| **Q1（待老猫确认）** | 「对已有数据库增删表」是否必须支持**直连的外部库** | 本规划按 **DR-27 只做自建库**；若必须动外部库，需另立 DR 并把 M5-A 升级为"危险区 + 影响面 + 显式开关"，工期与风险显著上升 |
| **Q2（待确认）** | M5 是否一次交付三轨，还是 M5-C+A 先发、M5-B 顺延 0.12.0 | 本规划默认三轨同版；§六末给出可裁剪路径 |
