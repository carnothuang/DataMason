# DataMason（数据瓦匠）— 产品一页纸

> 一句话：**用自然语言，把一个想法一小时变成一个可运行、可交互、可查询的信息系统。**

数据瓦匠不是写代码的工具，是把"想法 → 数据 → 界面 → 流程 → 工作台"整条信息化链路，压缩成一个 AI 全程伴随的对话式工作台。

> **v0.2（2026-09-15）**：对齐 v0.2 部署形态（一验证 = 一套独立部署），并按本文档 §九「决策裁决归档（DR-01~25）」完成开发启动前走查修订（里程碑口径、API 措辞、流程时点、演示数据）与开发期新增裁决。本页是方向与外部沟通基线；技术细节以《设计细化》的「技术实现参考」章节为准，跨文档裁决以本文档 §九 为唯一权威。

---

## 一、我们在解决什么问题

**背景事实**：日常工作、咨询与项目策划中，大量判断需要"跑一遍数据"来验证（市场规模、库存结构、流程效率、方案对比）。但传统信息化建设太重：立项、设计、开发、测试、上线，周期以月计、成本以项目计。

**核心矛盾**：为了一次验证，去做一个正式系统，**极不合算**。结果就是——大多数人选择不验证，凭经验和口才做判断。

**DataMason 的答案**：把验证型信息化的建设成本降到"几乎为零"，让**验证成为习惯**。瓦匠砌砖，DataMason 砌系统——一块数据一块数据地，把想法砌成能跑的东西。

## 二、目标用户

| 层级 | 画像 | 典型诉求 |
|---|---|---|
| 核心用户 | 个人决策者、咨询顾问、项目策划人 | 用数据支撑判断，向客户/合作方演示"可运行的系统" |
| 延伸用户 | 产品经理、售前顾问、创业团队、研究机构 | 快速出可演示原型，低成本试错业务方向 |
| 潜在用户 | 中小企业内部信息化需求方 | 把零散表格变成真正的业务系统 |

**共性**：不懂深度技术细节，但懂业务；要的不是代码，是**能跑、能看、能问的结果**。

## 三、六大核心能力

1. **秒建数据库** — 快速创建并连接常见数据库（SQLite / MySQL / PostgreSQL），本地可用、不绑平台。
2. **自然语言建表** — 用一句描述生成表结构，**严格遵循主外键与关联规范**，数据从第一秒就是"干净关系"。
3. **引用生成** — 基于已有表，生成可视化交互界面（MVP 只读浏览 / M2 完整 CRUD）、向导式业务流程（P2）、API 开放（P2）。
4. **菜单化组织** — 快速形成系统交互菜单，把零散页面拼成完整系统。
5. **工作台式信息归集** — 以工作台承载业务流程，供使用人员快速完成日常操作与数据录入。
6. **AI 伴随全程** — 自然语言构建数据库/界面/流程（MVP 即可）；在工作台上直接询问进度、数据反馈结果（**问答为 P3(M4)**，MVP 仅建表/建界面伴随）。

**一句话概括链路**：部署一套系统 → 数据库 → 表结构 → 界面与流程 → 菜单与工作台 → AI 全程兜底与问答（问答 P3 闭环）。

> **每套系统自带「操作日志」**（固定能力，不生成、不配置、不能关）：业务数据被谁、在什么时候、做了什么改动，始终可查、可回溯。验证往往要拉上小团队真用，出了"这条记录谁改的"的问题，翻日志就能还原现场。

## 五、差异化：凭什么不是"又一个低代码"？

| 对比对象 | 他们做什么 | DataMason 不同在哪 |
|---|---|---|
| 无代码表单/低代码平台（简道云、宜搭） | 绑平台、围绕表单 | **本地数据优先**、数据库优先，数据资产是自己的 |
| 数据库客户端（Navicat/DBeaver） | 手动运维数据库 | **自然语言建表**、自动外键规范，不懂 SQL 也能建模 |
| AI 编程助手（Cursor 等） | 面向代码、产出代码片段 | 面向**数据与业务**，产出物是"可运行的系统"，不要求代码素养 |
| 传统定制开发 | 以月计的正式项目 | 以小时计的验证系统，够用即止，跑完即弃/可升级 |

**本质差异**：DataMason 服务的对象是"决策与验证"，不是"交付与运维"。系统是手段，判断是目的。

## 六、典型使用场景

- **咨询验证**：客户说"库存周转有问题"，1 小时建出进销存模型，当场跑数据、出结论、演示界面。
- **投资/合作评估**：把对方给的报表导成数据关系，快速生成分析工作台，随手验证对方说法。
- **项目策划**：想法还很模糊，先建几个表跑一遍流程，验证业务逻辑是否闭环，再决定投不投入。
- **方案演示**：向客户/团队展示的不是 PPT，而是**能实际点击运行的系统原型**。

## 七、MVP 范围与迭代节奏（对齐设计细化·技术实现参考 M0–M4，2026-09-15）

| 阶段 | 范围 | 目标 |
|---|---|---|
| **MVP（P0 / M1）** | 部署清单 + 部署流（创建模式）+ 数据库连接管理 + 自然语言建表（含外键规范）+ 提案卡简版 + 表数据可视化浏览 + **就绪即带演示数据** + 首次启动向导（管理员账号 + LLM 配置） | 跑通"想法→数据→带数据的系统入口"最核心链路 |
| **P1（M2）** | CRUD 界面 + 成员与权限（三层角色、按人授权）+ **操作日志** + 直连已有库首版 | 跑通"数据→应用"，多人真用也能追溯 |
| **P2（M3）** | 菜单组装 + 工作台布局 + 向导式业务流程 + API 开放 + 演示模式 + 停止/销毁/分享（访客公开页面） | 变成完整可交付系统 |
| **P3（M4）** | AI 工作台问答（进度查询、数据反馈、自然语言调整） | 全程 AI 伴随闭环 |

> 说明：里程碑编号 M0–M4 以《设计细化》技术实现参考 §十 为唯一权威（M1–M4 对应 P0–P3，M0 为独立技术验证里程碑，不对应任何产品阶段）；业务流程由 P1 调整到 P2（向导式 v0）、"API 生成"收敛为"API 开放"（DR-06/11，见本文档 §九）。

**节奏原则**：快速验证、小步迭代——每一阶段都先服务老猫自己的咨询场景，用真实案例打磨。

## 八、成功指标（怎么算做对了）

- **建设成本**：从想法到可运行系统，目标 < 1 小时。
- **建模质量**：自然语言 → 表结构一次通过率（含外键规范）≥ 80%。
- **复用率**：已建系统在工作台中被再次打开使用的比例（验证"不是一次性玩具"）。
- **验证行为变化**：老猫团队在咨询中实际启用 DataMason 系统的次数（核心北极星——**敢验证**）。

### 二、两处需要工程特别注意的裁决细节

#### DR-03 两阶段日志（为什么不能承诺跨库事务）
业务写发生在部署的独立物理库，日志在元数据库——两个连接不可能共享事务，任何「同一事务提交、写日志失败回滚业务」的表述都写不进代码。固定写入顺序：① 元数据库写 `pending` 日志 → ② 业务写提交 → ③ 日志置 `committed`。②失败则删除①（业务报错、无日志）；③因进程崩溃缺席时，由启动对账任务收尾（pending 超时 → 回查该业务动作是否已生效：新增/删除查主键、修改查目标值，生效则补 finalize，未生效则丢弃）。留痕可靠性从「事务保证」降为「对账保证」——这是有意折中，代码注释、评审与运维文档均按此表述。

#### DR-02 按人分配（为什么不是菜单→角色）
两份产品文档的示例都是「小李：入库单+库存查询；小张：质检单+退货处理」——同为操作员、菜单不同。菜单→角色的存储表达不了这一点。落地：`deployment_members` 只存档位（creator/admin/operator），`deployment_menu_grants` 存每个人的菜单授权；操作员可见菜单=自己的授权集合，创建人/管理员=全量。UI 交互不变（仍是"把功能分给人"），只改存储模型。

### 四、维护规则（防再断档）

1. **决策先行**：任何跨文档的概念改动（状态、角色、里程碑、数据模型、能力范围），先在本节追加 DR 条目，再改三份规划文档。
2. **编号权威**：里程碑只允许 M0–M4（设计细化·技术实现参考 §十）；体验文档内部次序用 UI-n；不得复用 M 编号。
3. **术语对照固定**：五态=草稿/部署中/运行中/已停止/已销毁（演示=视图模式，不是状态）；角色=创建人/管理员/操作员（访客=访问者，不是角色）；功能分配=按人；部署完成动作=注册入口（不叫起服务）。
4. **能力增删必须留痕**：范围收缩或移动（如 API 生成→API 开放、流程 P1→P2）必须在本节写明原因与去向，禁止无声消失。
5. **技术可行性优先于产品承诺**：产品文档不得出现技术文档无法背书的保证（如跨库事务原子性）；发现时以 DR 形式裁决后双向同步。
6. **（新增）实现闭环说明**：凡涉及元数据模型新增/变更、部署流 UX 闭环、跨库身份，除 DR 条目外，必须附「实现闭环说明」（表间关联、接口契约、UX 步骤落库动作），防止一致性走查遗漏可落地性。
