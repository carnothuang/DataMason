## 三、缺陷与偏差（实测不符项）

### 🔴 高优先级

#### D-1 销毁部署未清理附件元数据与文件目录
- **违背**：DR-28「销毁级联清理」、技术方案 §4.4「`destroy_deployment` 级联加一步删除 `<stem>.files/` 目录」、M5-B-1 验收项「销毁清目录」。
- **实测**：上传附件后销毁部署，返回 `200 destroyed`，但
  - `attachments` 表**仍剩 1 行**；
  - `DATA_ROOT/deployments/deployment_<id>.files/` 目录**仍存在**，文件**未被删除**。
- **根因**：`server/deploy/service.py:610` `destroy_deployment` 级联清理了 `CrudConfig / PageSpec / FlowSpec / TableSpec` 等，**未处理 `Attachment`**，也未删除附件目录；且未产生 `pending_gc` 状态，`cleanup_orphans()` 无法回收（自测报告已披露启动回收未接线，但本项是"连标记都没有"）。
- **影响**：销毁后残留元数据行 + 磁盘文件无上限累积，与 DR-28 直接冲突。

#### D-2 附件预览存在存储型 XSS 面
- **违背**：DR-33 文件安全边界（技术方案 §4.3「扩展名白名单 + MIME 探测；未知/危险类型拒绝」）。
- **实测 A（客户端可伪造 MIME）**：上传文件名 `note.txt`、multipart part 的 `Content-Type` 伪造成 `text/html` →
  - 落库 `mime = text/html`；
  - `GET /files/{token}/preview` 返回 **200，`Content-Type: text/html; charset=utf-8`（inline）**，正文为 `<script>…</script>`。
- **实测 B（白名单自带矢量）**：`.svg` 在扩展名白名单内，上传后 `mime = image/svg+xml`，`/preview` 返回 **200 inline `image/svg+xml`** —— SVG 内联脚本在**应用同源**执行。
- **根因**：`is_inline()` 以 `text/` 前缀 + `application/pdf` 放行（`server/files/service.py:111`），而 `mime` 取自 `FileStorage.mimetype`（**客户端提供的 part Content-Type**），服务端未做「扩展名 → MIME」强绑定校验；`upload_allowed_mime` 配置项（技术方案 §2.4）**未实现**。已设 `X-Content-Type-Options: nosniff`，但对"声明类型本身就是可执行 HTML/SVG"无效。
- **影响**：已登录用户打开附件预览即可能在同源执行脚本（会话窃取）。建议：服务端按扩展名映射固定 MIME（忽略客户端 Content-Type）；`text/html`、`image/svg+xml` 强制 `attachment`；或预览走独立源/沙箱。

### 🟠 中等

#### D-3 停止态下文件上传与导入仍开放
- **违背**：M3-1「停止态入口不可操作」（开发计划 §一 已就位基线）、工程纪律第 7 条（服务端为安全边界）。
- **实测**（部署 `status = stopped`）：`GET .../rows` → **409**（正确）；但
  - `POST /api/files` → **201**（写入成功）；
  - `POST .../import/preview` → **200**；
  - `GET .../rows.xlsx` → **200**。
- **根因**：`server/files/routes.py` 与 `server/imports/routes.py` 直接调用 `crud_runtime._registry()`，**绕开** `workspace.routes._deployment_api()` 中的 `_assert_running()`。

#### D-4 必填列未映射未在预览阶段阻断
- **违背**：技术方案 §5.3「必填列未映射 → 阻断」。
- **实测**：上传仅含无关表头的 CSV（不映射必填列 `name`）→ 预览返回 `mapping={}, total=1, valid=1, error_count=0`（**全绿**）；提交时才由数据库抛错、以通用错误信息返回。
- **根因**：`server/imports/service.py:130` `_validate` 的 `check_cols` 仅取 `columns if c["name"] in mapping`，未映射列被整体跳过。
- **影响**：违反"永不盲写/先给错误清单"的提案式承诺；用户看到全绿后才在提交环节失败，体验与语义不一致。

#### D-5 导出增强仅部分交付
- **违背**：M5-B-5 验收项「选择导出列、上限可配置与提示」；技术方案 §5.4「列选择参数 `cols=a,b,c`」「上限从硬编码 5000 改为配置项；超限时明确返回"已导出前 N 行"」。
- **实测**：`GET .../rows.xlsx?cols=name` → **400**「未知过滤列: cols」（列选择未实现，且未识别参数被当作过滤列报错）；`config` 中**不存在**导出上限配置项（仅 `DM_IMPORT_MAX_ROWS`），`export_rows(max_rows=5000)` 仍为**硬编码**，无截断提示。
- **已达成部分**：`rows.xlsx` 可用、`export` 动作权限已服务端强制（403 生效）✓。M5-B-5 标记 ✅ 与验收项**不完全对应**。

#### D-6 删表未做服务端二次确认
- **违背**：技术方案 §3.3 接口契约 `POST .../tables/{name}/drop` 请求体 `{confirm: <表名>}`；DR-31「必须二次确认（输入表名或勾选确认）」；工程纪律第 7 条。
- **实测**：`server/deploy/routes.py:482` `confirm_drop_table` 不读取请求体，**不校验 confirm**；二次确认仅由前端 `DropTableModal.tsx` 承担。
- **影响**：绕开前端的直调 API 可一次性删表（虽仍受 `blocked` 守卫与创建人权限保护），安全边界未落在服务端。
